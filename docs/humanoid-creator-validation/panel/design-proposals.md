# Architecture proposals (Opus, one per angle, 2026-09-03)


## Explicit Rig

**Summary.** Delete FBX from v0.1 entirely and ship VRM 1.0 (.vrm = glTF 2.0 binary + a VRMC_vrm JSON extension) written by a pure-Swift writer the project owns outright. The thesis is in the name: VRM carries humanoid.humanBones as an EXPLICIT bone-name-to-node-index table, and UniVRM's Vrm10Importer reads it and calls humanoid.AssignBones(...) then CreateAvatar() -> HumanoidLoader.BuildHumanAvatarFromMap -> AvatarBuilder.BuildHumanAvatar at import time. That single fact deletes the largest un-testable risk in the PRD: Unity's AvatarAutoMapper is never invoked, so none of the heuristics the research digest documents from UnityCsReference source can bite us -- no keyword scoring (+20 for 'hand', -1000 for 'end'/'nub'/'wrist'), no minStep/maxStep valid-bone-step windows, no 'actual bone' weighting rules, no dummy-bone second pass, no 5-degree arm tolerance in sBonePoses, no 'Character not in T-Pose', no Configure step at all. The Avatar is built from data we authored, not guessed from the file. VRChat's SDK validates the Unity Humanoid Avatar (VRCSdkControlPanelAvatarBuilder.AnalyzeIK operates on the Animator's avatar), not the source file format, and VRChat's own docs only say the model must be 'in a format compatible with Unity' -- so a UniVRM-built Avatar should be as acceptable as an FBX-built one. Every FBX route in the digest carries an upstream defect we cannot fix; a ~1,500-line Swift GLB/VRM writer has only defects we can fix, and it is gated by the Khronos glTF-Validator, which runs headless on Linux via `npm i gltf-validator` with zero native deps.

**Stack.** iPadOS 17.5+; SwiftUI + MTKView/Metal app shell; ALL logic in one SwiftPM package that builds on Linux (Swift 6.3.3, verified working on Ubuntu 24.04 with XCTest + Swift Testing). No Objective-C++ anywhere -- the PRD's ObjC++ bridge is replaced with Swift/C++ interop (.interoperabilityMode(.Cxx)), which the in-repo probe at docs/humanoid-creator-validation/probes/swift-cxx-interop already proves builds and tests on Linux against real tiny_bvh.h and real ufbx.c. Math on Swift stdlib SIMD3/SIMD4 plus a hand-rolled Mat4 -- never Apple's `simd` module, which does not exist on Linux. Foundation only in the core: no simd, no Metal, no UIKit, no CoreGraphics, no ImageIO, no CryptoKit (use swift-crypto, which compiles to a free re-export of CryptoKit on Apple). Project generated by XcodeGen from a committed project.yml, which the digest verified builds and runs on Linux, so the agent defines the Xcode project without ever opening Xcode. Dependencies: tiny_bvh.h (MIT, C++), ufbx (MIT, C -- kept ONLY as a diagnostic reader, never a writer), swift-crypto, ZIPFoundation. Dropped from the PRD: Assimp, Autodesk FBX SDK, cgltf.

**Export route.** VRM 1.0 (.vrm), i.e. a glTF 2.0 GLB carrying the VRMC_vrm extension, produced by an owned pure-Swift writer; Unity side consumes it with UniVRM (MIT, com.vrmc.vrm + com.vrmc.gltf, requires Unity 2022.3 LTS+, which matches VCC's pinned 2022.3.22f1). Deliberately rejected, each on evidence: (1) glTF/GLB via Unity glTFast -- disqualified outright, it creates no Avatar of any kind, Humanoid or Generic; issue #391 has been open since 2022-05-02 and the digest's re-verification against glTFast 6.20.0 (2026-08-25) found zero Avatar/Humanoid entries across twelve releases since 6.13.0. (2) GLB via UnityGLTF -- it does build Humanoid Avatars, but via a bone-NAME table (AvatarUtils.CreateHumanDescription) plus reflection into Unity's internal AvatarSetupTool.SetupHumanSkeleton. That re-enters the heuristic minefield VRM exists to escape, and it has field failures ('LeftUpperLeg is missing', #796). Keep it documented as an alternate for Blender/other-engine interop only. (3) COLLADA .dae -- superficially attractive because Unity imports it natively with zero packages, but the digest's adversarial pass demolished it: Unity has NEVER documented DAE skin import (only DAE BLEND SHAPE import, on a different page), Unity's skinned-mesh doc names FBX exclusively, and Autodesk's own COLLADA conversion notes document dropping 'Normals (for skin and shape)' and 'Instances', being Y-up-only, and that export/import 'can destroy or produce unpredictable results for some elements'. Worse for this project specifically: there is NO headless oracle for DAE -- ufbx cannot read it and gltf-validator cannot read it -- so choosing DAE trades a documented, machine-checkable path for an undocumented, unverifiable one, which is exactly backwards given constraint (1). Assimp's ColladaExporter also hardcodes bind_shape_matrix to identity ('I think it is identity in general cases') and supports one skeleton per scene. (4) USD -- dead: com.unity.formats.usd deprecated 2024-11-15 and Intel-only on macOS; the successor com.unity.importer.usd requires Unity 2023.1+ and therefore cannot be installed in 2022.3.22f1 at all.

**End-user Unity steps.**
- ONE-TIME, step 1 of 3: Install Unity Hub and Unity 2022.3.22f1. Note the PRD is wrong here and the guide must be platform-aware: the Creator Companion GUI is Windows-only ('The Creator Companion is only fully-supported on Windows 10', with a Windows-only download). On macOS -- which is Mentis's own machine -- use Unity Hub + 2022.3.22f1 (Apple Silicon builds exist) plus either the official VPM CLI (`vpm check hub`, `vpm check unity`, documented and working on macOS well before 2.5.0) or the community ALCOM client. Do not point Mac users at a VCC GUI that does not exist.
- ONE-TIME, step 2 of 3: Create a VRChat Avatars project (VCC on Windows; `vpm new` or ALCOM on macOS). This is identical for the FBX route -- it is not a cost of choosing VRM.
- ONE-TIME, step 3 of 3 -- THIS IS THE ONLY GENUINELY EXTRA STEP VERSUS FBX: Window > Package Manager > + > Add package from git URL, and paste the UniVRM VRM10 package URL pinned to the exact version recorded in the app's validation data (com.vrmc.vrm; its com.vrmc.gltf dependency installs with it). Alternatively double-click the released .unitypackage. MIT licensed, one paste, done once per machine, never again. The exact URL string must be captured verbatim during the Phase-0B session and baked into the generated guide rather than guessed.
- PER AVATAR, step 1: Drag AvatarName.vrm into Assets/. UniVRM's ScriptedImporter generates a prefab whose Animator ALREADY has a valid Humanoid Avatar. Do not open the Rig tab. Do not press Configure. There is no Configure step and no 'Character not in T-Pose' dialog on this route -- that entire class of failure does not exist here.
- PER AVATAR, step 2: Drag the generated prefab into the scene. Add Component > VRC Avatar Descriptor. Place View Position between the eyes. Leave Lip Sync on 'Default' (the descriptor's Default mode 'has no lip sync attached to it', which is correct for a v0.1 mannequin with no visemes -- selecting 'Viseme Blend Shape' with no blendshapes yields silently non-working lip sync). Leave Eye Look disabled.
- PER AVATAR, step 3 (MOBILE ONLY, and the app's guide must say this because the PRD omits it entirely): select the imported material and switch the shader to VRChat/Mobile/Toon Standard. Mobile avatars are restricted to the VRChat/Mobile shader whitelist, and UniVRM's default MToon10 shader is not on it. Then select the albedo texture and set Max Size 1024 with ASTC compression for the Android/iOS build -- VRChat's Android guidance caps mobile textures at 1024x1024, mobile Texture Memory brackets are 10/18/25/40 MB, and the Android bundle has a hard 10 MB post-compression cap.
- PER AVATAR, step 4: Confirm Mesh Read/Write is enabled on the imported mesh. This is not optional pedantry -- VRChat downgrades any avatar with Read/Write disabled straight to Very Poor and the SDK blocks the upload until it is fixed. The generated Import guide must call this out with a screenshot.
- PER AVATAR, step 5: VRChat SDK control panel > Build & Publish. Select Windows + Android (+ iOS) in the Platforms dropdown (multi-platform build landed in SDK 3.7.6; 3.8.1 added iOS Build & Test). Windows + Android is the minimum for cross-platform visibility, because iOS falls back to the Android build with shader replacements when no native iOS build exists.

**Headless-testable estimate.** 75%

Finish with Build & Test to see the avatar on his own body in VRChat. He reports back a pass/fail plus the exact UniVRM package URL and version, and screenshots of the SDK panel. The Linux agent cannot measure input-to-photon latency and the digest is explicit that touch-vs-vsync phase varies per device by 8-33 ms with identical code -- only a device reading settles it. He reports numbers, not opinions; the agent tunes from the numbers.
- M3 JOURNEY GATE, ~1 hour: complete the entire user journey end to end on the iPad (new document, references, morphs, one grab stroke, fill + paint, four poses, export) and take the resulting avatar into VRChat via Build & Test. This is the PRD's own Phase-1 gate, unchanged.

The CI can measure triangle area ratio, flipped normals and joint cross-section collapse and clamp slider ranges automatically, but 'does this bend look like a person' is not a metric, and the digest is blunt that skin-weight quality cannot be automated to professional standard. This is the one place a human eye is load-bearing.
- TESTFLIGHT + SIGNING, ~1 hour, once: App Store Connect setup and the first upload. Optional and deferrable.

**Phase 0 gate.** Phase 0 splits into a Linux half the agent runs on every commit and a Mac half Mentis runs exactly once. PHASE 0A (agent, Linux, 3 days, zero Xcode): write VRMWriter in pure Swift, seeded directly from the 54-line working skinned-GLB spike already committed at docs/humanoid-creator-validation/probes/gltf-vrm/mkglb.py, which the research pass verified produces 0 errors / 0 warnings / 0 infos from the Khronos validator with skins, JOINTS_0/WEIGHTS_0, inverseBindMatrices and an embedded PNG. Emit the PRD's golden corpus (neutral T-pose; min and max height and shoulders; local displacement at elbow and knee; joint-rest relocation with recomputed inverse binds; a finger-weight sample; and deliberately malformed negatives) and drive it through FIVE independent Linux oracles that must all be green: (1) Khronos gltf-validator via `npm i gltf-validator` -- Apache-2.0, Dart-compiled-to-JS, zero deps, verified installing and running on this box -- requiring numErrors == 0 AND numWarnings == 0, and asserting on the specific skin codes SKIN_NO_COMMON_ROOT, SKIN_SKELETON_INVALID, SKIN_IBM_INVALID_FORMAT, INVALID_IBM_ACCESSOR_COUNT, ACCESSOR_JOINTS_INDEX_OOB, ACCESSOR_JOINTS_USED_ZERO_WEIGHT, NODE_SKINNED_MESH_LOCAL_TRANSFORMS; (2) ajv against the published VRMC_vrm-1.0 JSON schemas from the vrm-specification repo, checking specVersion, meta, and every required humanBone; (3) an ACTUAL PNG DECODE of the embedded IDAT -- this is not paranoia, the verification pass proved that Foundation's Data.compressed(using:.zlib) emits raw RFC1951 DEFLATE while PNG IDAT requires an RFC1950 zlib stream, and built a GLB that passes the Khronos validator 0/0 AND is reported as '1x1 rgb sRGB' while zlib.decompress fails with 'incorrect header check', because the validator only parses the PNG header and never inflates IDAT. A green validator does not certify the texture; only an inflate-and-compare-pixels test does; (4) Blender 5.2.1 headless as a second, independent importer -- `blender --background --python`, verified in this session running with DISPLAY unset, no GPU and no /dev/dri -- asserting the armature, bone hierarchy, vertex groups and UV layer reconstruct; (5) a CPU linear-blend-skinning oracle that skins the golden meshes at the four preview poses and matches the app's own Swift skinning to 1e-5. PHASE 0B (Mentis, one ~2-hour session): the touchpoint above. GATE CRITERION, one sentence, unchanged in spirit from PRD section 12: a physical iPad exports a deliberately modified skinned mannequin that the Khronos validator, Blender and Unity all agree is the expected Humanoid, and the VRChat SDK reports no rig-related blocker. STRETCH, half a day, worth attempting because it would collapse the Mac bottleneck: Unity 2022.3.22f1 ships a Linux Editor with documented `-batchmode -nographics -executeMethod`, so a CI job could import the .vrm with UniVRM and assert avatar.isValid and avatar.isHuman and dump the HumanDescription bone map without a Mac at all. Licensing activation in a container is the unknown; treat it as upside, never as the plan.

- M0-GATE -- Mentis's 2-hour iPad-to-VRChat session. Hard stop/pivot decision point. If UniVRM 1.0 into the VRChat SDK fails, pivot to VRM 0.x (see risks) before writing one line of editor code -- exactly the discipline the PRD demands, but now the gate is cheap enough to actually run.
- M1 -- Template freeze and offline forge (agent, 1 week, runs in parallel with M0-GATE). Headless Blender 5.2.1 on Linux (proven: subdivide, decimate, ARMATURE_AUTO bone-heat weighting on 1154/1154 verts, smart_project UV, Cycles-CPU bake, all returning FINISHED in ~1 second) drives the pipeline from MakeHuman's CC0 hm08 base to a frozen 8-10k-triangle template. Starting weights transferred from MakeHuman's CC0 default_weights.mhw by nearest-surface, then bone-heat as fallback, then limit-to-4 / X-mirror / smooth / RENORMALISE (mandatory -- the verification pass measured Blender's raw output summing to 0.976-0.994, not 1.0) / sort descending. Device QA, the technical-art deformation review, TestFlight, the automated safe-morph-range CI sweep (every morph extreme crossed with every preview pose, measuring triangle area ratio, flipped normals and joint cross-section collapse, clamping slider ranges where a metric fails rather than hand-authoring them).

**Risks.**
- THE ONE REAL RISK: no public evidence exists that a UniVRM-1.0-imported Humanoid prefab plus a VRC Avatar Descriptor uploads cleanly through the current VRChat SDK. The mechanism is verified from primary source -- Vrm10Importer.cs calls humanoid.AssignBones then CreateAvatar, HumanoidLoader.BuildHumanAvatarFromMap calls AvatarBuilder.BuildHumanAvatar, and VRChat's own SDK 3.10.4 validator operates on the resulting Unity Avatar rather than on any source file format -- but mechanism is not evidence. MITIGATION: it is the entire Phase-0B gate and costs two hours, not six weeks. FALLBACK IF IT FAILS: emit VRM 0.x instead. Both profiles are glTF plus a JSON extension block, so this is a change to one file's JSON shape and roughly one day of work, not a new exporter -- and 0.x is what esperecyan's VRM Converter for VRChat targets. Design the template so BOTH profiles are emittable from day one: T-pose rest, identity local bone rotations, model facing +Z. That costs nothing now and buys the fallback for free. (Do NOT plan on the esperecyan converter as the primary path regardless: v41.5.2 dates from 2025-01-22 and pins com.vrchat.avatars ^3.5.0 against a current SDK of 3.10.4.)
- THE SILENT PNG BUG. Verified experimentally during research: a GLB whose embedded PNG uses raw DEFLATE instead of a zlib-wrapped stream passes the Khronos validator with 0 errors and 0 warnings and is even reported as '1x1 rgb sRGB', while a real decoder rejects it -- because the validator parses the PNG header and never inflates IDAT. Swift makes this trap easy to fall into because Foundation's only compression API emits RFC1951 raw DEFLATE, and Foundation has no PNG encoder at all. MITIGATION: own PNGCodec target implementing the RFC1950 wrapper and Adler-32 by hand (a pure-Foundation STORED-block variant was proven to work and decode correctly), plus a CI test that inflates the IDAT and compares pixels. Never accept a green validator as texture proof.
- VRCHAT REQUIRES MORE BONES THAN VRM DOES, and the two rule sets interact in a way that will silently produce an unuploadable avatar if got wrong. VRM 1.0 requires 16 humanBones and makes chest and shoulders OPTIONAL; VRChat's shipping SDK source (com.vrchat.avatars 3.10.4, VRCSdkControlPanelAvatarBuilder.AnalyzeIK line 4143) hard-errors and returns false unless neck, both clavicles, pelvis, torso AND chest are all present -- 19 bones minimum. Worse, the shoulder/neck parent rule is CONDITIONAL: the SDK checks parentage against UpperChest if UpperChest is mapped and against Chest otherwise, so mapping UpperChest while parenting shoulders to Chest is a build-blocking error, and the stale rig-requirements doc page still describes only the unconditional Chest rule. MITIGATION: do not map UpperChest at all; parent LeftShoulder, RightShoulder and Neck directly to Chest; assert this parentage as an export-time blocking invariant. Also enforce shoulder height above 20 cm (an SDK error, not a warning) and make LowerArm the first child of UpperArm and Foot the first child of LowerLeg (warnings only, but getting them wrong silently breaks forearm and shin rotation in game).
- HANDEDNESS AND SCALE. glTF is right-handed, +Y up, front +Z, metres; Unity is left-handed. Every Unity glTF importer mirrors an axis on load, and UnityGLTF even ships a flipForward 180-degree escape hatch, which tells you people get this wrong. MITIGATION: the writer performs one deliberate, documented mirror (negate X on positions, normals and joint translations; flip triangle winding; conjugate rotations accordingly), and the golden corpus carries an explicit asymmetry marker so a mirrored export is caught by a test rather than by a user noticing their avatar's watch is on the wrong wrist. Assert height within 1% and feet on y=0 in CI.
- MOBILE STATS THE PRD DOES NOT TRACK. The PRD accounts for triangles, meshes, materials and bones but omits three ranked or blocking constraints: Texture Memory is a ranked mobile stat (Excellent 10 MB / Good 18 MB / Medium 25 MB / Poor 40 MB) that a 2048 albedo will bust unless Unity compresses it to ASTC; Android bundles have a HARD 10 MB post-compression cap that blocks upload and wear entirely; and mobile avatars are restricted to a shader whitelist that UniVRM's default MToon10 is not on. MITIGATION: default the export preset to 1024 for mobile, emit plain pbrMetallicRoughness rather than MToon so UniVRM maps to a swappable Standard/Lit material, and put the shader swap plus the ASTC and Mesh Read/Write settings in the generated Import guide as numbered steps with screenshots.
- MSL CANNOT BE COMPILED ON LINUX. Apple ships Metal Developer Tools for macOS and Windows only; Linux is not mentioned. A shader typo would therefore surface only when Mentis opens Xcode, which is precisely the cost this architecture exists to avoid. MITIGATION: put a GitHub Actions macos-26 runner (GA 2026-02-26, Xcode 26.6 default, iPad simulator runtimes preinstalled) in CI running `xcodegen generate` then `xcodebuild build` and `xcodebuild test -destination 'platform=iOS Simulator,name=iPad ...'` on every push. Unsigned simulator builds need no certificates. Keep shaders small and mirror every shader's math in a Swift reference function that IS unit-tested on Linux, so a shader is a transcription of tested code rather than a place where logic lives. With this runner in place, the only thing left that genuinely requires Mentis is the physical device and the Unity/VRChat leg.
- UNITY 6 MIGRATION LANDING MID-BUILD. VRChat is pinned to 2022.3.22f1 and rejects newer uploads outright, but the Unity 6 SDK and VCC were 'going through QA' as of the 2026-08-27 dev update and sit as In Progress on the roadmap dated 2026-09-01. MITIGATION: this route is markedly LESS exposed than FBX, because the fragile thing in a Unity version bump is the Humanoid auto-mapper's heuristics and Enforce T-Pose behaviour -- neither of which this pipeline touches. Still, store the target Unity version, the UniVRM package version and the rank thresholds in versioned validation data the app reads (the PRD already forbids hard-coding a marketing guarantee) and re-run the golden corpus the week the Unity 6 SDK beta ships.

**Why better than the PRD.** Three reasons, in order of weight. FIRST, IT MAKES THE GATE RUNNABLE. The PRD's Phase-0 gate can only be executed by Mentis, because both candidates are FBX and the only oracle that matters is Unity on a Mac. Under constraint (1) that is the worst possible shape: the agent writes code it cannot verify and waits for a human to tell it whether the code works. This plan moves five independent structural oracles onto the Linux box -- Khronos gltf-validator, VRM JSON schemas, real PNG inflation, headless Blender import, and a CPU skinning oracle -- so the agent gets a red or green light on every commit, and Mentis's session becomes confirmation rather than discovery. SECOND, IT REPLACES DEFECTS WE CANNOT FIX WITH CODE WE OWN. Every FBX writer available is broken in a way this project cannot repair. Autodesk's shipping iOS packages for 2020.3.7, .9, .10 and .11 contain arm64 and x86_64 objects stamped LC_BUILD_VERSION platform=macOS, so Xcode will not link them into an iOS target at all -- the only correctly-built iOS packages are 2020.3.2 and 2020.3.4, which means pinning to a 2020-era build, forgoing every subsequent fix, and still having no arm64 simulator slice. Assimp's FBX export epic #6142 stands at 0 of 10 completed with #5526 ('FBX not skinning correctly', open since 2024-04-03) sitting directly on the bind-pose path, its BindPose emission is commented out, and by default it merges vertices by position -- which breaks the PRD's own frozen-vertex-order invariant in section 10. ufbx-write is v0.2.0 with no tags, no releases, a self-declared breaking-changes warning, an open maintainer-filed bug (#30) about a missing skeleton root on exactly the armature path we need, and a skin unit test that asserts only face count and four vertex positions while checking nothing about weights, clusters or bind matrices. Against that, a ~1,500-line Swift GLB writer has a complete public specification, an official conformance validator, and only bugs we can fix the same afternoon. THIRD, IT DELETES THE HARDEST-TO-DEBUG FAILURE MODE OUTRIGHT. The digest spent an enormous amount of effort reverse-engineering Unity's AvatarAutoMapper from UnityCsReference source -- keyword scores, forbidden-word vetoes at -1000, valid-bone step windows, weighted-vertex qualification rules, a 5-degree arm tolerance -- and produced a long list of failure strings ('Required human bone X not found', 'Ambiguous Transform', 'X has bone length of zero', 'Character not in T-Pose') whose only diagnostic in the field is a red cross next to a Configure button. VRM does not run that code path. The bone map is data we wrote. AS A BONUS, IT FIXES FOUR REAL GAPS IN THE PRD: it adds texture memory, the mobile shader whitelist and the Mesh Read/Write requirement as tracked constraints; it adds export-time UV gutter dilation, without which the PRD's seam-partner stamping still produces visible halos under mipmapping; it replaces the ObjC++ bridge with Swift/C++ interop so the geometry layer is testable on Linux; and it corrects the PRD's macOS onboarding instruction, since the Creator Companion GUI Mentis is told to install does not exist for his machine.

**Weakest point.** Nobody has publicly documented a VRChat upload originating from a UniVRM-1.0-imported Humanoid prefab. The research found the mechanism in primary source -- Vrm10Importer.cs assigns the explicit bone map and calls AvatarBuilder.BuildHumanAvatar, and VRChat's own SDK 3.10.4 validator inspects the resulting Unity Avatar rather than any source format -- and found no VRChat document that rejects non-FBX sources. But it also found no document that affirmatively blesses one, and the only community VRM-to-VRChat converter targets VRM 0.x and is pinned to an SDK 19 months stale. So the load-bearing claim of this entire architecture is an inference from two codebases, not an observed result. Everything else here was executed and verified in-session: Swift 6.3.3 on Ubuntu 24.04 with XCTest and Swift Testing, Swift/C++ interop against real tiny_bvh.h and real ufbx.c, a 54-line skinned GLB passing the Khronos validator 0/0/0, gltf-validator installing from npm with zero native deps, Blender 5.2.1 running headless with no GPU and no display, XcodeGen generating a real iOS .xcodeproj from Linux. That asymmetry is the point rather than an embarrassment -- the unverified link is isolated to a single two-hour test that must be run before any editor code is written -- but it should be stated plainly: if Phase-0B fails and the VRM 0.x fallback also fails, this plan reverts to the PRD's FBX gate having spent three agent-days and two of Mentis's hours. A secondary and much smaller weakness: MSL still cannot be compiled on Linux, so shader errors reach a macOS CI runner rather than the agent's own loop, and Apple Pencil input-to-photon latency remains unmeasurable without a device.


## Plumb — Linux-Gated Native iPad Humanoid Creator

**Summary.** The PRD is right about the product, right about the immutable-contract thesis, and right that the export format is the project's only real risk. It is wrong about one thing: WHERE that risk gets retired. It puts the decisive proof on a physical iPad in front of a human, which under Mentis's constraint means the core risk can only be tested at human-session cadence — maybe twice a week.

Every FBX writer candidate is portable C/C++ that builds on Linux (Autodesk ships fbx2020310_fbxsdk_gcc_linux.tar.gz alongside the iOS package; Assimp builds on Linux and was verified end-to-end headless in one session; ufbx-write is single-file C99 with no OS-specific code). Every documented failure mode — bind-pose space, vertex order, bone hierarchy, T-pose angles, unit scale, weight normalisation — is detectable without an Apple device. So Phase 0 moves to Linux, and the iPad step shrinks to the one thing only it can prove: that the arm64 build links and produces a byte-identical file to the Linux build for the same snapshot.

Three refinements carry the design. (1) The Objective-C++ bridge becomes a plain C/C++ bridge consumed through Swift C++ interop (`.interoperabilityMode(.Cxx)`; the app target still sets SWIFT_OBJC_INTEROP_MODE=objcxx). ObjC++ cannot compile on Linux — there is no ObjC runtime in Swift there — so the PRD's bridge is the single line item that would have pushed TinyBVH, ufbx and the exporters off the testable surface. Swift/C++ interop with the REAL ufbx.c and REAL tiny_bvh.h was verified working from both XCTest and Swift Testing on Ubuntu 24.04 with Swift 6.3.3.

(2) `HumanoidGate` — a portable C++17 library that reimplements Unity's and VRChat's acceptance logic as testable predicates, from primary source I read this session: Unity's `AvatarAutoMapper` valid-bone/keyword/side rules, `AvatarSetupTool.sBonePoses` (UpperArm/LowerArm 5°, Hand 10°, Shoulder 20°, Hips/UpperLeg 15°, LowerLeg/Foot 20°, Spine/Chest/Neck 30°, thumb along (∓1,0,1) at 10/5/5), the zero-bone-length and duplicate-name errors, and VRChat SDK 3.10.4 `AnalyzeIK` at line 4093 — which blocks on 19 mapped bones (Unity's 15 plus Chest, Neck, both Shoulders), on shoulders/neck not parented to the highest mapped chest bone, and at line 396 on LeftUpperArm height < 0.20 m. The SAME library runs in `swift test` on Linux and as the app's on-device blocking-check pass. Unity's verdict stops being a thing only Mentis can obtain and becomes a thing the agent predicts and Mentis calibrates.

(3) The Autodesk FBX SDK is demoted from writer candidate to primary Linux validation oracle. Its iOS packages 2020.3.7/.9/.10/.11 are mis-built — every object is LC_BUILD_VERSION platform=macOS and Xcode will not link them into an iOS target; the last correct iOS build is 2020.3.4 (Xcode-12 era, iOS 7 min, no arm64 simulator slice). But Unity's importer IS the Autodesk FBX SDK, so reading our output back with the Linux build of that same SDK is the most predictive oracle available anywhere in this project — and internal dev-tool use sits squarely inside EULA §1.1.1 with no shipping question at all.

Everything else follows the PRD as written: one protected mannequin, fixed arrays and precomputed adjacency, raw Metal (RealityKit's LowLevelMesh has no joint semantics on iOS 18/26 and its deformation pipeline is iOS 27-only), SwiftUI document shell, TinyBVH picking, ZIP export, "Export for VRChat" never Publish, no custom FBX writer.

**Stack.** iPadOS 17.5+ (17.5 buys Pencil Pro squeeze/roll and UICanvasFeedbackGenerator; every 17.0 iPad runs 17.5). SwiftUI document shell (DocumentGroup, PhotosPicker, fileImporter) + MTKView via UIViewRepresentable, event-driven (isPaused=true, enableSetNeedsDisplay=true) with a 3-slot semaphore-gated position/normal ring buffer per Apple's triple-buffering guidance. Raw Metal renderer: GPU LBS skinning in the vertex shader, wireframe pass, grid, alpha-blended reference quads, UV-space paint pass. Raw UITouch (touchType == .pencil) with coalescedTouches/predictedTouches — NOT PencilKit, which gives no mid-stroke context.

Below the app, one SwiftPM package that is the whole testable surface: HumanoidCore (Swift, Foundation-only — no simd, no CoreGraphics, no CryptoKit; hand-rolled Mat4 on stdlib SIMD4<Float>, swift-crypto for SHA-256), HumanoidGate (C++17 acceptance predicates), GeometryBridge (C++17: TinyBVH wrapper, CPU LBS/DQS oracle, SculptGL-derived brush kernels, seam-partner stamping and JFA dilation reference, stb_image_write for deterministic PNG), UFBX (C), three exporter adapters behind one `FBXExporting` protocol, ValidationOracle (Autodesk-SDK-Linux + ufbx readback comparators), HumanoidBridge (Swift, .interoperabilityMode(.Cxx)). Xcode project generated by XcodeGen from a committed project.yml — XcodeGen builds and runs on Linux (needs USER/LOGNAME set), so the agent can smoke-test the spec it authors.

Deliberately excluded, on evidence: RealityKit and SceneKit (no joint semantics / deprecated at iOS 26); ModelIO, SCNScene.write and Entity.write (obj/stl only, .reality only, no documented skeleton export); PencilKit; nipplejs-style third-party UI; PMP; any Blender or MakeHuman runtime. Blender 5.2.1 headless and the `bpy` wheel are OFFLINE build tools only — the FBX exporter there is GPL-2.0-or-later and must never enter the app binary.

**Export route.** FBX 7400 binary, centimetre geometry, UnitScaleFactor 1, UpAxis Y, FrontAxis -Z. Centimetres because FBX's native unit is cm and Assimp hardcodes UnitScaleFactor 1 — author in metres against that and Unity imports the avatar at 1/100 scale. With cm geometry and Convert Units on (default, fileScale 0.01) a 165-unit mesh lands at 1.65 m with root scale 1.0, and LeftUpperArm sits ~1.35 m — inside VRChat's no-warning band (error below 0.20 m, "short" warning below 1.0 m, "tall" warning above 2.5 m). 7400 rather than 7500 because Blender writes 7400 and is the decade-proven Unity producer, and 7400 is what our golden reference file will be.

FBX structure: root → {"Armature" (Null) → Hips → …, "Body" (Mesh)}. Exactly one level of armature nesting — VRChat SDK 3.8.2+ blocks a nested armature outright. Mesh node named "Body", never "Head": Unity errors "Ambiguous Transform" if any transform name collides with a bone mapped to a human bone. No `*_end` leaf nodes anywhere — "end", "top" and "nub" score -1000 in Unity's auto-mapper and are hard vetoes. Bone names are Unity's own HumanBodyBones names (Hips, Spine, Chest, Neck, Head, LeftShoulder, LeftUpperArm, LeftLowerArm, LeftHand, LeftThumbProximal…, LeftUpperLeg, LeftLowerLeg, LeftFoot, LeftToes, LeftEye, Jaw): they hit every positive keyword and no forbidden one, and the "left"/"right" tokens satisfy the side regex. UpperChest is NOT mapped — mapping it MOVES the required attachment point, and shoulders/neck parented to Chest with UpperChest also mapped is a build-blocking error. LowerArm is the FIRST child of UpperArm, Hand the first child of LowerArm, same for legs.

Writer candidates, all three behind `FBXExporting`, all three built and gated on Linux, ranked as a prior the corpus is free to overturn:
A. **Assimp**, pinned to a master commit ≥ 2026-08-24 (post PR #6754, which derives cluster TransformLink from mOffsetMatrix) — NOT release v6.0.5, which still derives bind pose from the node hierarchy. Two mandatory mitigations: explicitly set the undocumented raw property `bJoinIdenticalVertices` to false (it merges control points by position and would silently destroy the PRD's frozen vertex-order invariant) with a regression test on the control-point count; and either accept no BindPose object (deliberately commented out upstream, with a rationale that the FBX SDK reconstructs it from clusters) or re-enable it behind a flag and A/B it. Most evidence today: its full skin chain was verified structurally correct in a headless round-trip.
B. **ufbx-write**, pinned commit (v0.2.0, MIT/Unlicense, two files). Best-fit API — skin deformers, clusters, bind poses, bones, materials, textures, its own deflate, and a genuinely derived FileId/footer hash rather than Blender's fixed-timestamp fake. Two known costs: it is pre-1.0 and self-declared breaking, and open issue #30 means `ufbxw_prepare_scene()` never emits a skeleton root — the caller must create `UFBXW_BONE_ROOT` explicitly. Prior art for the skinned path exists in the V-Sekai/godot branch `vsk-fbx-write-4.6`; read it before writing the adapter. Promote to A if it clears the corpus, because it has no vertex-merge trap, writes a real BindPose, and lets us pick 7400.
C. **Autodesk**, demoted to reader oracle. If it is ever used as a writer, pin 2020.3.4, `lipo -thin arm64` the ios-armv7 fat archive, wrap it with the x86_64 simulator slice as an XCFramework, and stub export on arm64 simulator.

PNG via stb_image_write (public domain, portable, deterministic) rather than ImageIO, so the Linux and iPad exports are byte-identical. Foundation's `Data.compressed(using: .zlib)` emits raw RFC 1951 DEFLATE, not the RFC 1950 container PNG IDAT requires — a naive Swift PNG writer produces a file the Khronos validator still passes and no decoder can read.

Package: `AvatarName.zip` = AvatarName.fbx, Textures/AvatarName_Albedo.png (1024 default, 2048 opt-in), Import_into_Unity.md (platform-aware), AvatarName_manifest.json (templateID/version, counts, estimated texture memory in both mobile brackets, SHA-256s, gate findings), and optionally HumanoidImportKit.unitypackage. The texture default flips to 1024: VRChat's Android guidance caps at 1024, a 2048 RGBA with mips is ~21.3 MB uncompressed (mobile Medium) versus ~3-6 MB as ASTC, the app cannot control Unity's import compression, and the Android bundle has a hard 10 MB post-compression cap. Paint internally at 2048 and downsample on export so canvas quality is not what gets sacrificed.

**Phase 0 gate.** Phase 0 passes when, for all eight positive corpus cases and at least one exporter candidate, ALL of the following hold — and fails otherwise, stopping editor work exactly as the PRD demands.

(a) BYTE-IDENTICAL EXPORT. The on-device iPad export of a given snapshot is byte-for-byte identical to the Linux export of the same snapshot. This is achievable because the writers are deterministic C/C++ and the only nondeterminism is CreationTime, which we pin to a fixed timestamp (exactly what Blender does). If it holds, every future exporter regression is catchable on Linux forever, and Mentis's device sessions stop being an exporter test.

(b) AUTODESK-SDK READBACK. The Autodesk FBX SDK Linux build — the same code Unity's importer uses — reads the file back with: vertex count and control-point order exactly equal to the authored arrays; UV0 identical; one to four normalised influences per vertex in descending order with |sum-1| < 1e-5; per-cluster Transform equal to the authored inverse-bind and TransformLink equal to the authored world rest transform, per bone, to 1e-5; UnitScaleFactor 1, UpAxis Y, FrontAxis -Z; one material with a relative PNG path. ufbx and Blender's LEGACY Python importer must agree (Blender 5.0+ ships a ufbx-based importer, so the new one shares a blind spot with our validator and does not count as independent).

(c) GATE PREDICTS PASS. HumanoidGate returns zero blocking findings: 19 mapped bones present (Unity's 15 plus Chest, Neck, both Shoulders); UpperChest unmapped; both Shoulders and Neck parented directly to Chest; Hips has a parent and is an ancestor of every humanoid bone; LowerArm the first child of UpperArm, Hand of LowerArm, LowerLeg of UpperLeg, Foot of LowerLeg; no two mapped-bone names colliding with any transform in the file including the mesh node; no `*_end`/`nub`/`top` names; no consecutive mapped pair closer than 5 mm; every single-child chain bone (Spine, Neck, Shoulder, UpperArm, LowerArm, UpperLeg, LowerLeg, Foot, Toes) carrying at least one non-zero weight, and the eye and jaw bones weighted too so they auto-map rather than being skipped as unweighted leaves; T-pose within Unity's sBonePoses tolerances (UpperArm and LowerArm 5 degrees, Hand 10, Shoulder 20, Hips and UpperLeg 15, LowerLeg and Foot 20, Spine/Chest/Neck 30, finger proximals 10 and intermediates/distals 5, thumbs along (∓1,0,1)); feet on the ground plane, hips centred on XZ; LeftUpperArm height between 1.0 m and 2.5 m; total height within 1% of the authored value.

(d) SKINNING AGREES. CPU LBS driven by the matrices READ BACK from the exported file matches the in-app reference skinning within 1e-4 m at every vertex across six poses: T, arms-down, elbow/knee bend, squat, forearm pronated 90 degrees, and thigh internally rotated. Structural equality is not enough — this is the check that catches the transform-space class of bug that ruins Assimp issue #5526 and is invisible to a counts-and-hierarchy diff.

(e) NEGATIVES REJECTED. All six deliberately malformed corpus cases are rejected by HumanoidGate with the specific expected finding code, not merely rejected.

(f) UNITY CONFIRMS. In one Mentis session, Unity 2022.3.22f1 auto-maps the file as Humanoid with no Configure errors and no "Character not in T-Pose", accepts a VRC Avatar Descriptor, and the VRChat SDK reports no rig-related blocking validation. **Risks.**
- HumanoidGate is a MODEL of Unity, and models drift silently. If my reimplementation of AvatarAutoMapper/AvatarSetupTool/AnalyzeIK is subtly wrong, the agent optimises against a wrong oracle for weeks with no signal, because Mentis only reaches Unity occasionally. Mitigation: unity-verdicts.json is a first-class CI fixture; every Mentis Unity session records the real verdict per corpus file, and a test fails on any disagreement. The gate is only trustworthy AFTER the first calibration, which is M0 day 6. Treat every gate verdict before that as a hypothesis.
- No exporter has EVER been publicly proven to produce a Unity-Humanoid-accepted skinned FBX. Assimp: verified structurally by ufbx round-trip, zero Unity reports in either direction, and its FBX-export epic #6142 sits at 0 of 10 with #5526 (bind pose taken from node hierarchy instead of authored inverse binds) open on exactly our path. ufbx-write: zero DCC validation anywhere public, open skeleton-root bug #30, pre-1.0, three months stale. Autodesk: four consecutive mis-built iOS packages. This is the PRD's own thesis and it survives every check I made. The gate is the mitigation; the pivot list stays live.
- Assimp's `bJoinIdenticalVertices` defaults to true when the exporter is invoked directly, merging control points by position and silently breaking the frozen vertex-order invariant. It is a raw string property with no AI_CONFIG_ macro, so it is undocumented and can regress on any Assimp bump. Mitigation: set it explicitly, assert the control-point count equals the authored vertex count in the corpus, and pin the commit.
- Template art quality is the one thing neither the agent nor CI can judge. Blender's bone-heat weights do not sum to 1, fail silently (parent_set returns FINISHED even when the solve failed and later bones get no weights at all), and Blender's own manual warns they often deform badly on complex rigs. A 9k-triangle retopologised mannequin that bends convincingly at shoulder, elbow, hip and knee is real character-technical-art work. Mitigation: inspect per-bone weights rather than the operator return value; ship the two roll poses so candy-wrapper is visible; budget two Mentis art-approval sessions and expect to spend them.
- The Autodesk EULA is a live constraint even in the reader-oracle role. Internal development use is explicitly permitted (§1.1.1), but the headers and libraries can never be committed or shipped in any public artifact (§2.1.1), and if any Autodesk code ends up linked into the app, the §1.1.5 attribution string must appear verbatim in both the About screen and the online documentation. GPL/AGPL code must stay out of the binary alongside it (§2.1.4) — which is also why Blender's FBX exporter is an offline tool and never a runtime.
- Metal shader errors cannot surface on Linux. There is no MSL compiler for Linux; Apple ships Metal Developer Tools for macOS and Windows only. Mitigation: macos-26 CI compiles every shader with `xcrun -sdk iphoneos metal` as a required check on every push, and every shader math function has a C++ reference twin tested on Linux — so shader bugs are compile errors caught by a robot, not behaviour mysteries caught by Mentis.
- VRChat pins Unity 2022.3.22f1 today, but the Unity 6 SDK was 'going through QA' as of the 2026-08-27 dev update and the roadmap listed it In Progress on 2026-09-01. Humanoid import behaviour (Enforce T-Pose, auto-map heuristics) is exactly what could move. Mitigation: the target Unity version and all rank thresholds live in a versioned validation-data file the app reads, never hard-coded; re-run the golden corpus the week the Unity 6 SDK beta ships.
- Texture memory is a ranked VRChat stat the PRD does not account for, and the app cannot control it: the bracket depends on the compression setting the Unity user picks. Mitigation: 1024 default, 2048 opt-in, estimated memory for both compressed and uncompressed printed in the manifest, ASTC named explicitly in the Unity steps — and the PRD's correct stance held, that the app reports counts and never claims a rank (since 2025.3.1 the rank players see is server-computed anyway).
- Byte-identical iPad-versus-Linux export is an assumption until M0 proves it. Floating-point differences between arm64 and x86-64 in the writer's own arithmetic, or an unpinned CreationTime feeding the FileId and footer hashes, would break it. If it does not hold, fall back to a structural-equality assertion on the readback — weaker, because it stops catching writer-internal regressions on Linux alone.
- Mac tooling is not what the PRD says. There is no official VCC GUI for macOS — only the VPM CLI or the community ALCOM client — and the VPM CLI's non-Windows unblock ships in the 2.5.0 BETA line while stable remains 2.4.5. Mentis's own first hour will hit this. Mitigation: the platform-aware install step is in the Unity instructions and in his setup checklist, not discovered live.

**Why better than the PRD.** The PRD's Phase 0 says: build a minimal iPad app, export on physical hardware, import into Unity, decide. That is the right TEST and the wrong PLACE. Under Mentis's constraint — an agent on Linux writes and tests, he only opens Xcode and validates — putting the decisive proof behind a device session means the project's only real risk is retired at human cadence, and every exporter iteration costs a person's evening. This proposal moves parts (a) through (e) of that same gate to Linux, where Autodesk ships the identical SDK API, Assimp builds and was verified headless end-to-end in one session, and ufbx-write is portable C99 with no OS-specific code. Mentis's Phase 0 shrinks from five days of blocking to one two-hour confirmation, and it becomes a CALIBRATION rather than a discovery.

Three factual corrections the PRD needs regardless of who builds it, each grounded in primary source rather than docs. First, the PRD's Objective-C++ bridge cannot compile on Linux — there is no ObjC runtime in Swift there — so as written it would have pushed TinyBVH, ufbx and every exporter off the testable surface. Swift C++ interop does the same job and was verified against the real ufbx.c and the real tiny_bvh.h from both XCTest and Swift Testing on Ubuntu. Second, the PRD says "Autodesk lists iOS and current SDK 2020.3.10". Every object in the 2020.3.7/.9/.10/.11 iOS packages carries LC_BUILD_VERSION platform=macOS; Xcode will not link them into an iOS target at all. The last correct iOS build is 2020.3.4, from a different CDN path, Xcode-12 era, with no arm64 simulator slice. That single fact would have consumed a day of the five-day spike as an unexplained linker error. Third, the PRD's rig requirement is Unity's 15 bones; the shipping VRChat SDK 3.10.4 blocks the BUILD unless Chest, Neck and both Shoulders are ALSO mapped, and unless both Shoulders and the Neck are parented to the HIGHEST mapped chest bone — so mapping UpperChest silently moves the required attachment point and turns a correct-looking rig into a blocked upload. Those are 19 bones with a coupled parentage rule, not 15, and it belongs in the frozen template contract rather than in a Unity-side surprise.

Beyond corrections, one addition changes the character of the project: HumanoidGate turns Unity's and VRChat's acceptance criteria into a portable C++ library that runs identically in Linux CI and on the iPad. The PRD says "Unity remains the source of truth", which is true and which, under this owner's constraints, makes Unity a serial bottleneck. Making the gate a predictive, calibrated, unit-tested model keeps Unity as the source of truth while removing it from the inner loop — and it means the app's own blocking checks and the CI's acceptance test are literally the same code, so a user never sees a green export that Unity rejects.

It also adds the one oracle that matters most and that the PRD does not have. Unity imports FBX through the Autodesk FBX SDK. Reading our output back with the LINUX build of that same SDK is far more predictive than a ufbx reopen, costs nothing to ship (it is a dev tool, squarely inside EULA §1.1.1), and sidesteps the whole distribution question. That is the highest-value use of a component the PRD was going to spend a legal review on.

**Weakest point.** HumanoidGate is the strongest idea in this proposal and also its biggest liability, and I want to be plain about that rather than sell it.

It reimplements, from source I read rather than from documentation, the private acceptance logic of two systems I cannot run: Unity's AvatarAutoMapper and AvatarSetupTool, and VRChat's VRCSdkControlPanelAvatarBuilder.AnalyzeIK. I verified the specific rules I am encoding — the sBonePoses angle table, the 19-bone requirement, the UpperChest-moves-the-attachment-point conditional at lines 4157-4166, the 0.20 m shoulder-height error at line 396, the first-child limb warnings — against the actual shipping source this session. But "the rules I encoded are right" is not the same claim as "the rules I encoded are all of the rules". Unity's mapper alone has behaviours that are easy to get subtly wrong and impossible to notice: hierarchy windows count VALID-BONE steps rather than transform depth, so an unweighted helper costs zero steps; a name keyword is worth +20 while a direction match contributes only +10 to score with the dot product going to a tie-breaker, so names outweigh geometry; a forbidden substring is a -1000 hard veto that no amount of correct geometry can overcome; and MapBones post-processes Hips upward and can collapse UpperChest into Chest, so the mapped result need not respect the very windows the search used.

The failure mode is quiet and expensive. A gate that is too STRICT is harmless — it rejects good files and someone notices immediately. A gate that is too LENIENT green-lights files Unity will reject, and because Mentis only reaches Unity every few days, the agent can spend a week optimising the template, the joint refit and the exporter against a wrong model and get consistent, confident, wrong answers the whole time. Every artifact will look correct. Every test will pass.

The mitigation is real but it is not free and it is not immediate: unity-verdicts.json as a CI fixture, a test that fails on any disagreement between prediction and recorded verdict, and a discipline that Mentis pastes Unity's actual result after every single session. Until the first calibration lands at M0 day 6, every HumanoidGate verdict in this plan is a hypothesis with no evidence behind it, and the honest thing to do in that window is to weight the Autodesk-SDK readback comparison — which tests observable file content rather than modelled behaviour — above the gate whenever the two point in different directions.

A secondary weakness worth naming in the same breath: three of my four validation oracles share ancestry. ufbx is the validator, Blender 5.0+ ships a ufbx-based FBX importer, and ufbx-write is by ufbx's author. Only the legacy Blender Python importer and the Autodesk SDK are genuinely independent, which is precisely why the Autodesk reader is load-bearing rather than a nice-to-have.


## Kaydara — a pure-Swift FBX 7.4 writer with a Linux-resident correctness loop

**Summary.** Write our own minimal FBX 7.4 binary writer in pure Swift and make Linux, not Xcode, the place where correctness is established.

The digest's verdict on every third-party writer is disqualifying on precisely the axis Mentis cares about. Autodesk's iOS packages are mis-built: .7/.9/.10 and .11 (2026-08-21) ship Mach-O objects stamped platform=macOS, so Xcode refuses to link them into an iOS target; only 2020.3.4/2020.3.2 carry real iOS slices (LC_VERSION_MIN_IPHONEOS 7.0, iOS 14.2 SDK, Xcode 12 era), there has never been an arm64 simulator slice, it adds ~14 MB, and whether Xcode 26 links iOS-7.0-min objects into an iPadOS 17 target is answerable *only on Mentis's Mac*. That is maximum Xcode-only debugging — exactly what constraint (1) forbids. Assimp needs a fork patch to strip `-DENABLE_BITCODE`/`-fembed-bitcode` (removed in Xcode 15) before it builds for iOS at all — another Mac-only unknown — and it violates the PRD's own core invariant: `bJoinIdenticalVertices` defaults true, so the geometry writer merges control points through `std::map<aiVector3D,size_t>` and the exported vertex count/order stops matching our frozen arrays. It also emits no BindPose, declares `ObjectType "NodeAttribute" Count: 1` while writing N (`count = 1; // TODO: select properly`), and carries an unfixed bind-pose bug (#5526, open since 2024-04-03). ufbx-write is genuinely well-engineered but is v0.2.0, untagged, unreleased, self-declared "breaking changes to be expected", ~3 months stale, and its `add_missing_skeletons` never emits `UFBXW_BONE_ROOT` — issue #30, the open Blender-armature roundtrip failure, sits directly on the skinned path we need, and `test_skin.h` asserts only face count and four vertex positions, so weights, cluster Transform/TransformLink and bind poses are untested.

Our scope is a fraction of any of theirs. We emit exactly one scene shape, forever: one Geometry, one Model/Mesh, N LimbNodes, one Skin, N Clusters, one BindPose, one Phong material, one FileTexture + Video. No animation, no morphs, no cameras or lights, no per-face materials, no importer, no general scene graph. Blender's `encode_bin.py` proves the container is 434 lines; Comfy-Org/fbx-exporter-three proves a from-scratch skinned writer in a scripting language is consumed by Unity. Estimate ~350 lines of encoder plus ~900 of semantic layer.

The payoff is the whole point: the writer is pure Swift + Foundation + system zlib, so it builds and unit-tests on the agent's Linux box with no C++ toolchain patch, no cross-compile, no bitcode flag, no iOS-slice archaeology. `swift test` exercises the identical bytes that ship. The only Xcode step left is linking a pure-Swift package into an app target — the least failure-prone link that exists.

Owning the writer also lets us enforce Unity and VRChat's real rules *before* export rather than discovering them in a Configure window. The scratchpad already holds `AvatarSetupTool.cs` (with `sBonePoses` at line 297: Hips 15°, UpperLeg (∓0.05,-1,0) 15°, LowerLeg (∓0.05,-1,-0.15) 20°, Foot 20°, and the 5°/5°/10° arm chain), `AvatarAutoMapper.cs`, `AvatarMappingEditor.cs` and `vrcsdk.cs`. Those transcribe directly into a Swift `VRChatRigGate` that runs on Linux in milliseconds against every morph extreme — a far tighter gate than "it reopened in ufbx."

**Stack.** Pure-Swift core, Linux-first, one thin Apple shell.

ONE SwiftPM package (`Package.swift`, `platforms: [.iOS(.v17), .macOS(.v14)]`) — no `.xcodeproj` inside it — plus one generated app target. Targets:

- `HumanoidCore` (Swift, Foundation only, zero Apple frameworks): hand-rolled Vec3/Vec4/Quat/Mat4 — NOT `simd`, which does not exist on Linux; stdlib `SIMD3<Float>`/`SIMD4<Float>` are fine and portable. Frozen template arrays + precomputed adjacency/symmetryPairs/seamPartners; `HumanoidDocument` as a Codable value type; morph apply; landmark-mean joint refit + rest-frame + IBM recompute; SculptGL-derived brush kernels (falloff `3d⁴−4d³+1`, inflate `intensity·r·0.1`, Blender's stroke-start-frozen Grab semantics); CPU LBS reference — deliberately LBS not DQS, because Unity's stock SkinnedMeshRenderer is LBS and a DQS preview would hide the candy-wrapper artefacts the user must see; UV-stamp + seam-partner + dilation reference; invariants.
- `FBXWrite` (Swift + CZlib): `FBXBinaryEncoder` (~350 lines), `FBXSceneBuilder` (~900), `FBXTemplates` (Definitions/PropertyTemplate blocks transcribed verbatim from Blender output, never invented), `FBXConstants` (Blender's fixed CreationTime `1970-01-01 10:00:00:000`, FileId, footer id, and the `f8 5a 8c 6a…29 0b` magic — a decade of proven Unity acceptance, and cheaper than ufbx-write's XOR-key derivation).
- `PNGWrite` (Swift + CZlib): ~150 lines. **Never** `Data.compressed(using:.zlib)` — Apple documents that as raw RFC 1951 deflate with no header and no Adler-32, while PNG IDAT requires an RFC 1950 zlib stream. The digest's GLB spike hit this exactly: glTF-Validator reported 0 errors and "1x1 rgb sRGB" on a file whose IDAT `zlib.decompress` rejects with "incorrect header check". Link real zlib instead.
- `CZlib`: systemLibrary target with a modulemap. `libz` ships in the iOS SDK and as `zlib1g-dev` on Linux — same API, both platforms, no vendoring.
- `VRMWrite` (Swift): GLB container + `VRMC_vrm`. ~500 lines on the same `ExportSnapshot`. Insurance track (see risks).
- `UFBX` (C99): vendored ufbx.c/.h — validator and CPU-skinning oracle. Verified compiling as a SwiftPM C target and callable from Swift on Linux.
- `GeometryBridge` (C++20 + `.interoperabilityMode(.Cxx)`): TinyBVH behind a small POD-boundary class. **Replaces the PRD's Objective-C++ bridge** — there is no Objective-C runtime in Swift on Linux, so ObjC++ would be untestable by construction. Plain C++ interop keeps it green on the agent's box. Remember: every dependent target must also enable `.Cxx`, and Linux uses libstdc++ where Apple uses libc++.
- `HumanoidCLI` (executable): the corpus driver the agent actually runs.
- `swift-crypto` for SHA-256 manifest hashes, not CryptoKit (absent on Linux; swift-crypto re-exports CryptoKit on Apple and uses BoringSSL elsewhere). `ZIPFoundation` works on Linux given zlib.

`Apps/HumanoidApp` — SwiftUI + MTKView, generated by XcodeGen from a committed `project.yml`. It contains **no algorithm**: view code, gestures, Pencil input, PhotosPicker, document plumbing, MTKView setup and five `.metal` passes (skinned mesh, wireframe overlay, grid, reference planes, UV-space paint). ImageIO survives only for HEIC/JPEG *decode* of reference images, which never enter an export.

Toolchain, day one: Swift 6.3.3 on Ubuntu 24.04, with `SWIFT_FORCE_MODULE_LOADING=prefer-interface` pinned in the Dockerfile. Without it `swift test` fails out of the box even for XCTest-only packages, because the 6.3.3 tarball ships a `Testing.swiftmodule` stamped 6.1.2 and the Linux frontend will not fall back to the `.swiftinterface` (swiftlang/swift#62550). Also export `USER`/`LOGNAME` or XcodeGen aborts.

Shaders: MSL cannot be compiled on Linux (Apple hosts macOS and Windows only). Two mitigations, both required — every shader's math is mirrored by a tested Swift reference function, and a GitHub Actions `macos-26` runner (Xcode 26.6, iPad simulators preinstalled) runs `xcodegen generate` + `xcrun -sdk iphoneos metal` + `xcodebuild test` on every push. CI does the Xcode build; Mentis does device and Unity.

**Export route.** Primary: `AvatarName.zip` = `AvatarName.fbx` + `Textures/AvatarName_Albedo.png` + `Import_into_Unity.md` + `AvatarName_manifest.json`.

FBX specifics, each chosen against a digest fact:

- **Version 7400 binary**, not 7500. Blender ships 7400 and it is what Unity's Autodesk-SDK importer has consumed for a decade; 7500's only byte-level difference is u64 node headers and a 25-byte NULL record. Take the path with the most Unity mileage.
- **Encoding 0 (uncompressed arrays).** Assimp does this and imports fine; the ZIP absorbs the size. It removes zlib from the FBX path entirely and makes every array byte-inspectable in a test.
- **Centimetre geometry with `UnitScaleFactor` 1, `UpAxis` Y, `UpAxisSign` 1, `FrontAxis` -Z.** FBX's native unit is cm; Unity's Convert Units then yields root scale 1.0 and 1 unit = 1 m. Writing metres with UnitScaleFactor 1 is the silent 100× that the digest flags as an unflagged Assimp risk. Asserted by a height-within-1% test.
- **Normals and UVs `ByPolygonVertex` / `IndexToDirect` with an identity index array.** Blender carries a permanent workaround for this: "Unity FBX import issue where the normals are considered invalid if any normals are deduplicated" (#123088). We never deduplicate.
- **`PolygonVertexIndex` with the last index of each polygon bitwise-NOT'd**; `LayerElementMaterial` AllSame `IndexToDirect [0]`; one `Layer 0`.
- **Skeleton: no leaf bones, no `*_end` nodes.** Unity's auto-mapper scores `end`/`top`/`nub` at −1000 and rejects any candidate scoring ≤0 — a joint named `foot_end` can never map regardless of position.
- **Bind data written once, from one source.** Node rest transform == Cluster `TransformLink` == T-pose, all identical, identity/uniform scale on bones. Unity samples the skin's bind pose first, compares its T-pose error against the node rest pose, and starts from whichever is closer — so any disagreement between the two is a coin flip we lose half the time. Joint relocation updates the node transform and the cluster together and recomputes `Transform` = inverse of the new global rest.
- **`Pose`/`BindPose` emitted** (Type BindPose, Version 100, NbPoseNodes, a PoseNode for the mesh and every bone). Assimp deliberately omits it; Blender and Comfy both write it. We write it, and keep it behind a flag so the corpus can A/B it in Unity.
- **`Definitions` counts correct.** Assimp's are not (Pose declared 1 with 0 written; NodeAttribute declared 1 with N written) and it still imports, so tolerance exists — but we have no reason to spend that tolerance.
- Material `FbxSurfacePhong`; `Texture`/`FbxFileTexture` + `Video`/`FbxVideo` with `RelativeFilename` = `Textures/AvatarName_Albedo.png`; OP connection to `DiffuseColor`.
- Skeleton root and the skinned mesh are **direct children of the single FBX root** — no extra "Armature" wrapper. VRChat SDK 3.8.2 added a blocking upload error for nested armatures.
- Footer: Blender's constants verbatim. ufbx never parses the footer, so this gets its own byte-level test rather than relying on a round-trip.

Insurance output: **VRM 1.0** (`.vrm` = GLB + `VRMC_vrm`), ~500 lines over the same `ExportSnapshot`. Reason: it is the only export path with a Khronos-grade Linux validator (`npm i gltf-validator`, `validateBytes`, verified 0 errors / 0 warnings on a hand-written 54-line spike), and `VRMC_vrm.humanoid.humanBones` is an explicit bone-name→node-index map, so UniVRM's `Vrm10Importer` calls `AvatarBuilder.BuildHumanAvatar` directly and the user never touches Configure. Not a pivot — a parallel three-day deliverable that keeps constraint (3) reachable even if FBX needs another week. glTFast is not an option: it creates no Avatar of any kind, issue #391 open since 2022 and still absent from the 6.20.0 changelog (2026-08-25).

**Risks.**
- A self-consistent transform-space error passes every Linux oracle and fails only in Unity. This is the single most likely way the plan fails, and it is structural: ufbx is our validator, Blender's default FBX importer is ALSO ufbx since 5.0, so those two share a common-mode blind spot. Mitigations: run ufbx at strict=true with disable_quirks; require Blender's LEGACY Python importer as the one genuinely independent parser; structurally diff against a Blender-exported golden file rather than judging our output on its own; and attempt the Unity-on-Linux batchmode spike early, because if it lands the risk collapses entirely.
- Units and axes. FBX's native unit is centimetres; writing metre geometry with UnitScaleFactor 1 imports at 1/100 with no error anywhere. The digest flags this as an unflagged risk in Assimp's own output. Mitigation: cm geometry + UnitScaleFactor 1 + UpAxis Y + FrontAxis -Z, matching Blender's Unity-targeted output, with a height-within-1% assertion in both the ufbx test and the Unity checklist.
- Unity's Autodesk-SDK importer may be stricter than any reader we can run — Definitions template counts, Connections wiring, PropertyTemplate contents. Evidence cuts both ways: Assimp ships mismatched Definitions counts and imports fine, so tolerance exists, but we cannot measure it. Mitigation: transcribe Blender's Definitions and PropertyTemplate blocks verbatim rather than inventing them; spend no tolerance we do not have to.
- `Data.compressed(using: .zlib)` emits raw RFC 1951 deflate with no zlib header and no Adler-32, which is NOT what PNG IDAT requires. The digest reproduced this exactly: a GLB passed glTF-Validator with 0 errors while its PNG was undecodable. Mitigation: link system zlib through CZlib on both platforms; never touch Foundation's compression API; assert the PNG round-trips through a real inflate in a test.
- Template quality is human technical-art work and is the real schedule risk, not the writer. MakeHuman's body is 26,756 triangles and no CC0 proxy lands in the 8-10k band; bone-heat weights need a visual pass; and the digest is explicit that a green numeric gate has been necessary-but-not-sufficient more than once. Mitigation: budget a real character TA pass, freeze and certify one curated template, and gate on elbow/knee/finger pose renders rather than on metrics alone.
- The VRChat rule set is transcribed from SDK 3.10.4 source and SDKs move (3.8.2 added the nested-armature blocker; 3.10.4 changed the shoulder-parentage rule to follow UpperChest when mapped). Mitigation: keep every threshold, bone name and tolerance in a versioned validation-data JSON the app reads, never hard-coded, exactly as the PRD's own risk table demands. Same for VRChat's rank numbers.
- Unity 6's VRChat SDK was 'going through QA' as of 2026-08-27 with the roadmap listing it In Progress on 2026-09-01. Humanoid import behaviour is the part most likely to shift. Mitigation: 2022.3.22f1 stays the frozen target; re-run the corpus the week the Unity 6 SDK opens, and treat that as a scheduled event rather than a surprise.
- Swift-on-Linux toolchain traps that silently cost a day each: the stale Testing.swiftmodule breaking `swift test` even for XCTest-only packages; the bpy wheel being pinned to exactly one Python version per Blender release with no Linux aarch64 wheel at all; C++ interop requiring `.Cxx` on every dependent target and one stdlib per platform. Mitigation: pin all of it in the Dockerfile at M0, not when it bites.
- Two of the eight proportion controls could, at their extremes, push a joint outside Unity's per-bone T-pose tolerance (5 degrees on the arm chain is tight) or collapse a joint pair below the zero-length threshold. Mitigation: VRChatRigGateTests sweeps every extreme and every pairwise extreme, and slider ranges are CLAMPED where a metric fails rather than being authored by feel.

**Why better than the PRD.** The PRD's Phase 0 puts the highest-risk, least-testable work on the scarcest resource in the project. Both of its exporter candidates require a Mac to even attempt: Autodesk's iOS packages are mis-built through 2020.3.11 and the viable pin (2020.3.4) is an Xcode-12-era iOS-7.0-min static archive whose linkability into an iPadOS 17 target under Xcode 26 literally cannot be established anywhere but on Mentis's machine; Assimp needs a fork patch to strip bitcode flags before it compiles for iOS at all. The PRD then makes the entire editor conditional on that Mac-bound gate. My version moves the failure surface to the place with unlimited cheap iteration — Linux, one agent, `swift test` in seconds — and reduces Mentis to a checklist he runs once. That is constraint (1) satisfied structurally rather than by intention.

It also closes a real hole in the PRD's gate. The PRD's oracle is "reopen with ufbx", but `ufbx_load_opts.strict` defaults OFF — ufbx is documented as deliberately loading partially broken files, ships `disable_quirks`, `connect_broken_elements` and scene sanitisation, and never parses the footer at all. A clean default ufbx parse is close to no evidence. My gate runs ufbx strict with quirks disabled, adds a second genuinely independent parser (Blender's legacy Python importer), adds a structural diff against Blender's decade-proven Unity-accepted output, and adds a CPU-skinning cross-check through ufbx's `geometry_to_bone` at five poses — which is the only test that can catch the bind-space inconsistency the digest names as the top failure mode for hand-written FBX.

Third, it fixes a blocking omission. The PRD's blocking checks list "required bones; hierarchy" without saying which. The real answer, read from shipping SDK 3.10.4 source, is 19 bones — Unity's 15 plus Chest, Neck and both Shoulders, enforced by `AnalyzeIK()` as an `OnGUIError` that throws `ValidationException` and gates the build button — plus Shoulders and Neck parented to the highest mapped chest bone, a 20 cm minimum shoulder height, a zero-bone-length check, unique mapped-transform names, forbidden name keywords, weighted single-child chain bones, three finger bones minimum per hand, and Unity's per-bone T-pose angle table. Every one of those is now enforceable on the iPad before export and testable on Linux against every morph extreme. Under the PRD, each would have been discovered one Mentis-session at a time.

Fourth, it protects the PRD's own core invariant. The PRD's contract is frozen vertex/index/UV order and exact array counts — and Assimp, its candidate A, merges control points by position by default via `std::map<aiVector3D,size_t>`. Adopting it would have quietly broken the product's central promise, and the PRD has no test that would have caught it. A writer we own emits our arrays 1:1 by construction and asserts it.

Fifth, it deletes four Mac-only workstreams outright: no Autodesk EULA and App Store legal review, no XCFramework/lipo slice surgery, no `-fembed-bitcode` fork maintenance, no CMake cross-compile debugging. And it removes ~14 MB or ~1.5 MB of third-party binary from the app in favour of ~1,300 lines of Swift we can read.

I am not disputing the PRD's judgement that a custom FBX writer is a format-engineering project — it is, and the digest's 2-4-weeks-to-first-Unity-green estimate is credible. What has changed since the PRD was written is that all three alternatives have been examined at the byte and source level and each is disqualified on Mentis's specific constraints, while the writer's cost has moved almost entirely into the one place where iteration is free. The PRD's rule was right for a team with a Mac in the loop. It is the wrong rule for this one.

Last: the PRD offers GLB/VRM only as a Plan-B pivot triggered by failure. I ship it in week two as a three-day parallel deliverable on the same `ExportSnapshot`, because it is the only export path with a Khronos-grade Linux validator and because VRM 1.0 carries an explicit bone map that makes UniVRM build the Humanoid Avatar with no Configure step at all. That makes constraint (3) — the end user reaches a working VRChat avatar — independent of the FBX gate's timing.

**Weakest point.** The semantic layer of the FBX writer has no headless oracle that proves Unity acceptance, and the oracles I do have are less independent than they look.

ufbx is lenient by default and never parses the footer. Blender's default FBX importer has been ufbx-backed since 5.0, so "ufbx says yes" and "Blender says yes" are substantially the same opinion. That leaves exactly two genuinely independent Linux signals: Blender's legacy Python importer, and a structural diff against Blender's own exporter output. Neither is the Autodesk FBX SDK, which is what Unity actually uses and what we cannot run on Linux. If our Cluster `Transform`/`TransformLink`, our PoseNode matrices, our bone `Lcl` transforms and our GlobalSettings units are wrong in a mutually *consistent* way, every Linux test passes and Unity is silently wrong — and the digest identifies that exact class as the most common reason a self-written FBX fails in Unity. That is also, uncomfortably, the class of bug that looks like success right up until Mentis opens Configure.

I have three defences and I want to be honest that none is complete. The Blender structural diff converts "undocumented semantics" into "match this proven reference", which is strong but only covers the parts of the tree Blender also emits. The CPU-skinning cross-check catches bind-space errors that are *internally* inconsistent, which is most of them, but not one that is uniformly wrong. And the M4 session is scoped to diagnose rather than merely pass, so a failure yields information.

Which is why the Unity-on-Linux batchmode spike is the highest-value unknown in the entire plan and belongs on day one or two, not at the end. Unity 2022.3 ships a Linux editor; `-batchmode -nographics -executeMethod` is documented; Unity's own `TestAndValidateAutoSetup` shows the exact assertion sequence (reimport, "Did not find Avatar after reimport", "Avatar is not valid after reimport", "Avatar has invalid pose after reimport"); and `AvatarSetupTool.IsPoseValid` is reachable by reflection. The blockers are licence activation in a container and whether 2022.3.22f1 imports FBX headlessly on Ubuntu 24.04, which is outside its officially supported 18.04/20.04 list. Nobody has published either answer. If it works, the last real oracle moves onto the agent's box, Mentis's Phase-0 session becomes pure confirmation, and the weakest point in this architecture stops existing. If it does not, this plan runs on three-quarters of an oracle stack and the honest expected cost is one or two extra Mentis sessions at M4 — which is still fewer than the PRD's two-candidate spike would have consumed before it produced any answer at all.


## Humanoid Web — a zero-build Three.js PWA at /humanoid, VRM-first, no Xcode

**Summary.** Ship the humanoid creator as a Vercel-hosted Three.js PWA in the repo's existing house style (vanilla ES modules, pinned CDN Three, zero build step), sibling to /gauntlet, /sculpture and /ar. Mentis validates by opening a URL in iPad Safari, not by opening Xcode.

This is not a downgrade of the PRD — it is a re-siting of its single riskiest bet. The PRD's own Phase 0 exists because nobody can write a skinned FBX on iOS with confidence, and the research confirms that fear on all three candidates: Autodesk's "iOS" packages 2020.3.7/.9/.10/.11 contain zero iOS objects (504 Mach-O members each, all LC_BUILD_VERSION platform=macOS; only the 2020.3.4 CDN relic has real arm64 iOS slices, with no arm64 simulator slice in any version ever); Assimp's exporter carries "// TODO, FIXME: this won't work if anything is not in the bind pose", has BindPose emission commented out, merges control points by position by default (breaking the PRD's frozen vertex-order invariant), and sits in a 0-of-10 open FBX-export epic; ufbx-write is v0.2.0, untagged, unreleased, three months stale, with a maintainer-filed open bug (#30) on the exact skeleton-root path a humanoid needs and a skin unit test that asserts only face count and four vertex positions.

The web route sidesteps that wall by changing format, not ambition. A skinned GLB is JSON plus one ArrayBuffer. This repo ALREADY contains the proof: docs/humanoid-creator-validation/probes/gltf-vrm/mkglb.py is 54 lines and emits a skinned GLB with JOINTS_0/WEIGHTS_0, inverseBindMatrices, an embedded PNG and a skeleton root that the Khronos glTF-Validator passes at 0 errors / 0 warnings / 0 infos. In JavaScript that writer is smaller still and runs identically in the browser and in Node.

VRM 1.0 then converts the hardest remaining unknown into a table lookup. VRM is glTF plus a VRMC_vrm extension whose humanoid.humanBones is an EXPLICIT bone-name-to-node-index map. UniVRM's Vrm10Importer reads it and calls humanoid.AssignBones(...) then CreateAvatar() -> AvatarBuilder.BuildHumanAvatar, assigning animator.avatar at import. The user never opens Configure. Compare the FBX path, where acceptance depends on Unity's AvatarAutoMapper heuristic: keyword scoring (+20 per match), -1000 vetoes for names containing "end"/"top"/"nub"/"palm"/"wrist", a valid-bone rule where unweighted single-child chain bones vanish from candidacy entirely, hierarchy-step windows counted in weighted joints rather than transforms, and a T-pose gate that demands UpperArm and LowerArm within 5 degrees of the arm axis. VRM deletes that entire failure surface.

The pen story is far better than I expected and I verified it rather than assuming. MDN browser-compat-data gives PointerEvent.pressure, tiltX/tiltY, twist and pointerType at Safari 13; and getCoalescedEvents(), getPredictedEvents(), altitudeAngle and azimuthAngle all at Safari 18.2, mirrored to iPadOS. Safari shipped the full Pointer Events Level 3 pen surface in December 2024. Any iPad on a current OS in September 2026 exposes coalesced sub-frame samples AND prediction — the two things Apple's own WWDC15/16 latency guidance names as the difference between ~4 frames and ~1.5 frames of touch-to-photon lag. Missing versus UIKit: Pencil Pro squeeze, barrel roll (rollAngle), hover z-distance, and touchesEstimatedPropertiesUpdated. None is load-bearing for Grab/Inflate/Smooth plus a round paint brush.

Export works: navigator.share({files}) is Safari 14+, and this repo already ships it in production (Birb Mobile's results Share button attaches a rendered canvas JPEG via Web Share Level 2). showSaveFilePicker is absent in Safari, so the export is <a download> into Files plus a Share-sheet path — two taps, no App Store.

Architecture keeps the PRD's real product decision untouched: the immutable contract. One frozen template, fixed vertex/index/UV order, authored weights, authored morphs, precomputed adjacency/symmetry/seam tables, no half-edge mesh, no topology mutation. Only the host platform and the output container change.

**Stack.** Vanilla ES modules, no bundler, no transpile, no npm at runtime — the repo's stated house rule, and here it is also the core testing strategy: the exact same .js files are imported by iPad Safari and by `node --test` on the Linux container. No jsdom for the math, no build artifact that can diverge from what ships.

Rendering: Three.js pinned from esm.sh, matching gauntlet/src/core/three-loader.js. WebGLRenderer (WebGL2) is the shipping renderer. WebGPU is available (navigator.gpu, Safari 26, mirrored to iPadOS 26) but stays behind a flag — the repo's own capabilities note from 2026-06-11 says a WebGPURenderer migration "needs a real device-tested branch, not a blind merge", and nothing in this app needs compute.

Layout at /humanoid (its own directory, airtight against the parent like gauntlet/ is; add it to sw.js SIBLING_ARTEFACTS — visiting it must not overwrite Birb Mobile's offline shell under the './index.html' cache key, the exact live bug already fixed for /AR):

  humanoid/
    index.html                 host page, splash, UI chrome
    src/core/       template.js (frozen arrays loader), document.js, invariants.js
    src/edit/       morphs.js, joints.js (landmark-mean refit + IBM recompute),
                    brushes.js (grab/inflate/smooth, ported from SculptGL's
                    3d^4-4d^3+1 falloff and 0.15r dab spacing), symmetry.js
    src/paint/      uvpass.js (UV-space rasterisation), dilate.js (jump flood),
                    strokes.js (distance-resampled dab log)
    src/pick/       three-mesh-bvh wrapper (MIT; refit() after each stroke —
                    the direct analogue of TinyBVH, in JS, so it tests headlessly
                    and the Objective-C++ bridge disappears entirely)
    src/export/     glb.js (~500 lines), vrm.js (VRMC_vrm block), png.js, zip.js
    src/input/      pointer.js (coalesced + predicted + pressure/tilt)
    src/render/     viewport.js, skinning via THREE.SkinnedMesh
    tools/          humanoid-shot.mjs, validate-corpus.mjs, golden/

Skinning: THREE.SkinnedMesh (GPU, linear blend — deliberately NOT dual-quaternion, because Unity's stock SkinnedMeshRenderer that VRChat runs is LBS, and a DQS preview would hide exactly the candy-wrapper and joint-collapse artefacts the user needs to see before export). SkinnedMesh.applyBoneTransform gives the CPU skinning oracle in the same library, so preview and validator cannot drift.

Painting: render-to-texture in UV space — vertex shader emits gl_Position = vec4(uv*2-1, 0, 1) and varies world position/normal; fragment evaluates the brush footprint against the Pencil ray hit in world space. Dabs crossing a UV seam land on every island automatically, so the PRD's precomputed seam-partner map becomes a test oracle rather than the mechanism. Gutter dilation is a jump-flood ping-pong (11 passes at 2048). Undo is a dab-descriptor log replayed from an RT checkpoint every 8 strokes — cheaper than tile readback on mobile, and deterministic because dabs are already distance-resampled.

Persistence: OPFS (Safari 15.2+) for the document package, IndexedDB for the manifest index, both wrapped in try/catch. Safari evicts storage for sites unused for seven days, so "Save a copy to Files" is offered as the durable backup and the onboarding says so plainly.

Dev-only, never shipped: gltf-validator (npm, Apache-2.0, zero deps), @gltf-transform/core as an independent reader, ajv against the vrm-specification JSON schemas, headless Blender 5.2.x LTS via the bpy wheel for template forging and as a second import oracle, Playwright + Chromium for the screenshot/behaviour harness.

**Export route.** PRIMARY: .vrm (VRM 1.0 = GLB + VRMC_vrm), written by a hand-rolled ~500-line JS GLB writer. No third-party export library at runtime.

Why hand-rolled is safe here and was not safe for FBX: the glTF container is fully normative and mechanically checkable (accessor byteOffsets multiples of component size and 4-byte aligned, POSITION min/max required, byteStride required when attribute accessors share a bufferView, skin.joints must share a common root, inverseBindMatrices a FLOAT MAT4 accessor with count >= joints.length, GLB = 12-byte header + JSON chunk padded 0x20 + one BIN chunk padded 0x00). FBX's byte layer is equally documented but its SEMANTIC layer is not, which is why Blender needed nine years of fixes and ufbx-write's author — the most experienced FBX reverse-engineer alive — still has an open armature round-trip bug after a year.

The VRMC_vrm block is a static table: specVersion, meta, and humanoid.humanBones mapping the 16 required bones (hips, spine, neck, head, L/R upperArm/lowerArm/hand/upperLeg/lowerLeg/foot) plus chest and both shoulders to node indices. Because the skeleton is frozen, this file is authored once and never computed.

SECONDARY, same writer, extension block omitted: AvatarName.glb, shipped in the ZIP for Blender and other engines.

CANDIDATE C, gated and never promised: AvatarName.fbx via a vendored, pinned copy of Comfy-Org/fbx-exporter-three (TypeScript, ~4,582 lines, skinning + BindPose + morphs, a `unity` preset, FBX 7400/7500, one open issue). It runs in Node in CI; output is reopened by headless Blender — whose default FBX importer since Blender 5.0 IS ufbx (bpy.ops.wm.fbx_import) — and structurally diffed against a Blender-authored golden FBX of the same template. It ships only if it passes the corpus, and its failure never blocks a release. Note the deliberate contrast with needle-tools/three-fbx-exporter, which states outright that skinning, bones and bind poses are not supported.

Format choices explicitly rejected, with reasons:
- Autodesk FBX SDK: moot (no native binary), and mis-built anyway — .7/.9/.10/.11 iOS packages are 100% macOS objects; last real iOS build is 2020.3.4 from a stale CDN path; no arm64 simulator slice has ever existed.
- Assimp: position-keyed control-point merge is ON by default and destroys the PRD's frozen vertex-order invariant; BindPose commented out; bind-pose TODO in source; no primary evidence anywhere of a Unity import of an Assimp-exported skinned FBX in 2025-2026.
- ufbx-write: pre-1.0, untagged, self-declared breaking, open skeleton-root defect on the skinned path.
- COLLADA .dae: Unity imports it natively but Autodesk's own conversion notes document dropped "Normals (for skin and shape)", dropped instances, Y-up only, and "can destroy or produce unpredictable results for some elements"; Assimp's DAE exporter writes zero blendshapes and hardcodes bind_shape_matrix to identity.
- glTF via Unity glTFast: verified through glTFast 6.20.0 (2026-08-25) — no Avatar of any kind is created on import; issue #391 has been open since 2022-05-02. Never route the user there.

Texture: one 2048x2048 sRGB albedo via canvas.toBlob('image/png'), with a 1024 preset as the recommended mobile default — VRChat's Android guidance caps mobile avatar textures at 1024x1024, and texture memory is a ranked stat the PRD omits entirely (mobile Excellent <=10 MB, Good <=18 MB).

Package: AvatarName.zip containing AvatarName.vrm, AvatarName.glb, Textures/AvatarName_Albedo.png, Import_into_Unity.md, AvatarName_manifest.json (SHA-256 via crypto.subtle, not CryptoKit). Delivered by <a download> into Files, plus navigator.share({files}) for AirDrop straight to the Mac — Safari 14+, and already shipping in this repo.

**Risks.**
- Pen feel, not pen data. The data is confirmed present (pressure/tilt/twist at Safari 13; coalesced, predicted, altitude and azimuth all at Safari 18.2, mirrored to iPadOS). Mitigation: measure on day 3; keep dabs distance-resampled so appearance is event-rate independent regardless.
- The VRM-to-VRChat leg is source-verified but never publicly demonstrated end-to-end. UniVRM's Vrm10Importer calling AvatarBuilder.BuildHumanAvatar is read directly from shipping source, but the research found NO primary report of anyone uploading a VRChat avatar from a UniVRM 1.0 prefab; esperecyan's VRM Converter targets VRM 0.x only, last released 2025-01-22 and pinned to com.vrchat.avatars 3.5.0 against today's 3.10.4. Mitigation: this is Half B of the gate, discharged on day 3 before any editor work.
- UniVRM is an extra Unity package, which the PRD calls a 'Plan B product pivot' because it breaks the no-extra-importer promise. This is a real cost being deliberately traded for a deterministic Humanoid map and a strict headless oracle. It must be stated in onboarding, not buried.
- No App Store presence. A PWA installs to the Home Screen but has no listing, no discovery surface, no App Store payments, and a weaker install affordance. If Mentis wants a purchasable product rather than a Vibe Academy artefact, this route needs a different monetisation answer — and note the market signal that VRoid's iPad app now carries ad banners as of v2.14.0 (June 2026).
- Safari storage eviction and tab discard. Safari evicts site storage after seven days of non-use, and iPadOS can discard a backgrounded tab under memory pressure. A document-based creative tool that silently loses work is worse than one that never existed. Mitigation: OPFS autosave after every committed operation, an explicit 'Save a copy to Files' path, and honest copy about it.
- VRChat is mid-migration to Unity 6. The client beta has been live since 2026-06-25 and the SDK/VCC were 'going through QA' as of 2026-08-27 with the roadmap listing it In Progress on 2026-09-01. Humanoid import behaviour is exactly what could move. Mitigation: keep the target Unity version and every rank threshold in a versioned validation-data file the app reads (the PRD already forbids hard-coding a marketing guarantee); re-run the corpus the week the Unity 6 SDK beta ships.
- The template still needs real character technical art. Nothing here removes that. Bone-heat weights do not sum to 1 in Blender's output (measured: per-vertex sums 0.976-0.994, so normalisation is mandatory not cosmetic) and, worse, a failed heat solve is reported as a WARNING while parent_set still returns {'FINISHED'} — a headless script that checks the operator return value will ship an unweighted mesh without noticing. Verify by inspecting per-bone weights, never by return status.
- Zero build step versus a growing codebase. The house rule is right for shipping and for testability, but a UV-paint pipeline plus an exporter plus a document model is more code than /gauntlet. Mitigation: hard module boundaries, node --test on every pure module, and no cleverness that a browser cannot import directly.

**Why better than the PRD.** It attacks the constraint Mentis actually stated. He asked to maximise what is headlessly testable and minimise Xcode-only debugging. The PRD's own delivery plan names four serial bottlenecks that "more parallel agents will not remove": Xcode linking, physical-device Pencil testing, Unity import, and technical-art corrections. This route deletes the first outright, shrinks the second from a build-sign-install cycle to a page refresh, leaves the third unchanged (no plan can avoid it), and leaves the fourth unchanged (nor should it). Two of four bottlenecks gone for a format change.

It deletes the gate that was most likely to fail. Every FBX writer candidate is broken for this exact case, verified first-hand rather than inferred: Autodesk's current iOS packages contain no iOS objects; Assimp's default vertex merge breaks the PRD's own frozen-order invariant and its bind-pose handling carries a FIXME; ufbx-write is 0.2.0 with an open skeleton-root bug. Meanwhile a 54-line Python GLB writer already sitting in this repo passes the Khronos validator at 0/0 with skin, IBMs and an embedded texture.

It swaps a lenient oracle for a strict one. ufbx documents leniency as the default — strict is opt-in, and it ships disable_quirks, connect_broken_elements and scene sanitisation because it is built to load broken files. A clean ufbx parse is weak evidence that Unity's Autodesk-SDK importer will agree. glTF-Validator is a conformance checker with dedicated skin error codes, runs headless with one npm install and zero dependencies, and is already vendored in this repo's probes.

It replaces a heuristic with a table. Unity's FBX Humanoid path runs AvatarAutoMapper: keyword scoring, -1000 vetoes on names containing end/top/nub/palm/wrist, a valid-bone rule where unweighted single-child chain bones are invisible to the mapper, hierarchy windows counted in weighted joints not transforms, ambiguous-transform failures on duplicate names anywhere in the tree, and a T-pose gate demanding arms within 5 degrees. VRM's humanBones is an explicit node-index map and UniVRM builds the Avatar for you. Pages of failure modes collapse into a static table authored once.

It is the repo's own proven house style. Four Three.js artefacts already ship from here — Birb Mobile, Gauntlet, Bronze, Birb AR — with a Playwright harness convention (non-zero exit on any page or console error) that this project reuses verbatim. Birb AR already renders a Three.js game into a WebGLRenderTarget over a live camera feed on iPad Safari, and Birb Mobile already shares a generated file through the iOS Share sheet in production. The unknowns here are smaller than the unknowns the repo has already retired.

And the cost profile changes shape. The PRD budgets 6-9 weeks for a strong iOS/Metal engineer, 3-5 months for a solo developer learning Metal, skinning and FBX. This route removes Metal, Swift, Objective-C++, the Autodesk EULA legal review, a ~14 MB static library, code signing, TestFlight and App Store review from that scope, and it ships by `git push`.

**Weakest point.** The whole route bets that iPad Safari's pen path is good enough for a tool whose entire value is pen-driven — and that is the one claim I cannot settle on the Linux box, cannot settle from documentation, and cannot fix if it fails.

I verified more than I expected to: Safari 18.2 shipped pressure, tilt, altitude, azimuth, coalesced events AND predicted events, all mirrored to iPadOS. The input DATA is there, and prediction in particular is the thing I assumed would be missing. But data availability is not stroke feel. Apple's own latency guidance is a stack of native levers — MTKView.enableSetNeedsDisplay for event-driven paint, CAMetalLayer.maximumDrawableCount pinned to 2 to stay double-buffered, presentsWithTransaction with commit/waitUntilScheduled/present, suppressing Core Animation animations mid-stroke because they disable low-latency mode — and a WebGL2 canvas inside WebKit's compositor exposes none of them. Apple's own developer forums record that touch delivery phase relative to vsync varies by DEVICE with identical code, producing 8-33 ms swings. Nobody publishes a web-versus-native Pencil latency number for a 120 Hz iPad, and I could not find one.

So the honest position is: the first sculpt stroke Mentis makes on the glass either feels like a tool or feels like a web page, and no amount of work on this container moves that needle beforehand. Mentis's bar is explicitly "a GREAT result, not a demo". If it lands on the wrong side, the fallback — a strength slider and speed-derived falloff — is not a wash against native, it is a visibly worse product, and the correct response would be to reconsider the native route rather than paper over it.

That is also why the gate is three days and why the pen check is the FIRST thing in Half B rather than an afterthought at the end. It is the cheapest possible way to buy the answer, and it should be bought before a single brush is written.


## Anvil — Thin iPad, Headless Forge

**Summary.** The PRD makes its first, hardest, most-human-dependent milestone the one component that adds zero user value: an FBX writer running on iOS. Every candidate has a named, verified defect. Autodesk's "iOS" packages for 2020.3.7/.9/.10/.11 contain arm64 objects stamped LC_BUILD_VERSION platform=macOS and will not link into an iOS target at all; the last genuinely iOS-built package is 2020.3.4 (armv7/armv7s/arm64, LC_VERSION_MIN_IPHONEOS 7.0, iOS 14.2 SDK), static .a only, no arm64 simulator slice, four security releases behind. Assimp needs a pinned master commit past PR #6754 (2026-08-24, not in v6.0.5), never writes a BindPose, mis-declares its Definitions counts, and defaults bJoinIdenticalVertices=true — which merges control points by position and silently destroys the PRD's own frozen-vertex-order invariant. ufbx-write is v0.2.0 with no tags, three months stale, and carries open issue #30: prepare_scene never emits UFBXW_BONE_ROOT, so Blender cannot read armatures out of its skinned output. And the empirical precedent is Nomad Sculpt: four years to ship FBX export, still developer-flagged in 2.8 as unusable when the mesh has UVs or textures.

Anvil deletes that milestone. The iPad never writes FBX. It writes one deterministic file — a VRM 1.0 GLB — using ~600 lines of portable Swift over a vendored miniz, and a headless companion does the final mile. The document is not a compromise format: VRMC_vrm.humanoid.humanBones is an explicit HumanBodyBones→node index map, so the Unity side calls AvatarBuilder.BuildHumanAvatar with a hand-supplied HumanDescription and never touches the ModelImporter, the auto-mapper, Enforce T-Pose, bind-pose reconstruction, or unit/axis conversion. Every failure mode catalogued in the research — the -1000 forbidden-keyword veto, the 5-degree UpperArm tolerance, "bone length of zero", "Ambiguous Transform", valid-bone-step depth windows, Chest-vs-UpperChest shoulder parentage — is a property of Unity's guesser, and the guesser is simply not in the loop.

The payoff is that the entire chain runs in CI on Linux with no Apple hardware. I re-ran it in this container: a stdlib-only skinned GLB writer produces a file the Khronos Validator passes at 0 errors / 0 warnings / 0 infos, Blender 5.2.1 imports it headlessly with no GPU and no display, and the same Swift 6.3.3 package that compiles for iPadOS compiles and unit-tests on Ubuntu with real ufbx and real tiny_bvh.h linked through C++ interop. The device-side acceptance test then collapses to one line: the .vrm the iPad exports must SHA-256 match the .vrm CI already produced from the same document. That turns "does export work on the iPad" from an unanswerable format question into a hash comparison.

Three VRChat requirements make the Unity-package route not merely equivalent but strictly superior to shipping an FBX: Mesh Read/Write disabled forces Very Poor and blocks upload outright; mobile avatars are restricted to the VRChat/Mobile shader whitelist; and texture memory is a ranked stat (mobile 10/18/25/40 MB) where a 2048 albedo lands Excellent only once Unity compresses it to ASTC. An FBX in a ZIP cannot set any of the three. An importer sets all three before the user sees the prefab.

**Stack.** iPad: SwiftUI + MTKView/Metal, iPadOS 17.5 minimum (17.5 buys UIPencilInteraction.Squeeze, UITouch.rollAngle and UICanvasFeedbackGenerator; every iPad on 17.0 runs 17.5). Raw UITouch with coalescedTouches/predictedTouches, not PencilKit — PencilKit owns its renderer and gives no mid-stroke access to a Metal canvas. Not RealityKit: LowLevelMesh.VertexSemantic has no joint-index or weight member on iOS 18/26, its deformation pipeline (MeshDeformerComponent, SkinningDeformer) is iOS 27-only, its picking needs ShapeResource.generateStaticMesh regenerated after every stroke, and it appears capped at 60fps on ProMotion. Not SceneKit: deprecated across all platforms at iOS 26.

Core: one SwiftPM package that builds identically on iPadOS and Ubuntu 24.04 under Swift 6.3.3. Foundation-only — no simd module (unavailable on Linux; use stdlib SIMD3<Float>/SIMD4<Float> and a hand-rolled Mat4), no CryptoKit (swift-crypto, which compiles to a CryptoKit re-export on Apple), no ImageIO, no CoreGraphics, no Compression, and critically no Objective-C++ anywhere — the Linux toolchain bakes in -disable-objc-interop, so the PRD's ObjC++ bridge would be the one layer the agent could never compile. C++ is reached through .interoperabilityMode(.Cxx) instead, which I verified working against the real ufbx.c (33,204 lines) and real tiny_bvh.h (9,375 lines).

Vendored C: miniz (public domain, single file) for RFC-1950 deflate, PNG encoding and the ZIP writer. This is load-bearing and replaces three PRD dependencies. Foundation has no PNG encoder at all, and its only compression API emits RFC-1951 raw DEFLATE with no zlib header and no Adler-32 — I built that exact file and the Khronos Validator passes it at 0/0/0 while zlib refuses it with "incorrect header check". A green validator report does not certify a texture. miniz also makes output byte-deterministic across Apple and Linux, which system zlib would not, and it retires ZIPFoundation.

Also vendored: tiny_bvh.h behind a POD C++ wrapper for Pencil picking with per-stroke Refit; ufbx (test targets only) as the reader oracle.

Offline/CI, never shipped: Blender 5.2.1 LTS pinned (bpy wheel is locked to Python 3.13 exactly — 5.0.x was 3.11), Khronos gltf-validator 2.0.0-dev.3.10 via npm, Unity 2022.3.22f1 in batchmode, XcodeGen built from source on Linux for project generation.

**Export route.** iPad writes ONE file: AvatarName.vrm — a GLB carrying the baked skinned mesh, the fixed skeleton, inverse-bind matrices, the embedded 2048 sRGB albedo PNG, and a VRMC_vrm extension whose humanoid.humanBones block is an explicit bone-name → node-index table. Alongside it in the export ZIP: AvatarName_manifest.json (templateID, templateVersion, the eight morph values, SHA-256 of the .vrm, tri/bone/material counts as guidance only) and Import_into_Unity.md. No FBX leaves the iPad.

VRM 1.0 rather than plain GLB for three concrete reasons. It carries the explicit humanoid map so no importer anywhere has to guess bones. Its spec mandates T-pose rest, +Z front (matching glTF, unlike VRM 0.x's -Z) and positive bone scale — constraints the app already satisfies by construction and can assert. And it gives a free fallback: UniVRM's Vrm10Importer already calls humanoid.AssignBones then CreateAvatar → AvatarBuilder.BuildHumanAvatar, producing a Humanoid Avatar with no Configure step, so if my importer were unavailable the file is still usable through a shipped MIT package.

PRIMARY final mile — com.mentis.humanoid, a small UPM/VPM package the user installs once. A ScriptedImporter registers .vrm-from-Anvil and produces a prefab directly, exactly the pattern UniVRM uses. It parses only the constrained glTF subset we ourselves emit (we own both ends, so the reader is a few hundred lines, not a general glTF implementation), builds the Mesh with bindposes and the bone Transform array, then calls AvatarBuilder.BuildHumanAvatar with a HumanDescription assembled from the file's own bone table. It then does the four things an FBX cannot: sets Mesh Read/Write enabled (off = Very Poor and a hard upload block), assigns VRChat/Mobile/Toon Lit or Standard Lite from the mobile whitelist, sets the texture importer to ASTC 6x6 for Android and iOS so texture memory lands in the Excellent bracket, and adds VRCAvatarDescriptor under #if VRC_SDK_VRCSDK3 with ViewPosition derived from the head bone. Hips is emitted as a direct child of the avatar root with no intermediate Armature node, because SDK 3.8.2 added a hard upload block for nested armatures.

The importer then runs VRChat preflight against the rules read out of the shipping SDK source (VRCSdkControlPanelAvatarBuilder.cs, AnalyzeIK at line 4093) and fails the import with a named rule rather than letting the user hit an opaque SDK error: all 19 bones mapped — Unity's 15 plus Chest, Neck and both Shoulders, which the SDK errors on and returns false; both Shoulders and Neck parented to the highest mapped chest bone (we deliberately never map UpperChest, so that is Chest, and the two decisions stay uncoupled); shoulder height ≥ 0.20m or it is a build error; LowerArm the first child of UpperArm and Foot of LowerLeg, which is only a warning but silently breaks forearm and shin rotation in-game.

SECONDARY final mile — Companion/blender/glb_to_fbx.py, run as `blender --background --python`. This is the FBX escape hatch and the agent's structural oracle. Blender's exporter is the most Unity-proven FBX writer in existence: Unity's own .blend import path shells out to bpy.ops.export_scene.fbx. But the flags must be set explicitly, never inherited — Unity's live branch passes none of the humanoid-relevant ones and so inherits add_leaf_bones=True and use_armature_deform_only=False, precisely the two settings VRChat rigs need off. defaults_unity3d() is dead code with zero callers in the entire Blender tree and is reachable from Unity only through a branch requiring io_scene_fbx.export_fbx, a module deleted in Blender 2.80. So the script sets, verbatim: add_leaf_bones=False, use_armature_deform_only=True, primary_bone_axis='Y', secondary_bone_axis='X', apply_scale_options='FBX_SCALE_ALL', apply_unit_scale=True, axis_up='Y', axis_forward='-Z', bake_anim=False.

**Phase 0 gate.** FIVE DAYS, ALMOST ENTIRELY IN CI. The question is not "can an iPad write FBX" — it is "can a deterministic file produced by portable Swift become a VRChat-uploadable Humanoid with no Configure step and no FBX writer on iOS." Nothing in steps 1-6 needs Xcode or a physical iPad.

1. LINUX — Forge an interim template. 2. LINUX — `swift run anvil-export` emits four .vrm files from the SAME HumanoidCore + writer code the iPad will later call: neutral T-pose, height-min, height-max, and elbow-displaced-plus-joint-relocated with recomputed inverse binds.

3. LINUX — Structural validation. Khronos gltf-validator must report 0 errors AND 0 warnings. VRMC_vrm validated against the published JSON schemas via ajv. The validator only parses PNG headers; I built a GLB whose IDAT is raw DEFLATE and it passed 0/0/0 while being undisplayable. Assert on a set of image codes, never on the report alone.

4. **Risks.**
- Unity Editor batchmode on Linux may not license non-interactively. This is the plan's single load-bearing unknown; the research flagged it UNKNOWN twice and never settled it. Mitigation: prove or disprove it on day 1 of M0, not day 5. Fallback is a GameCI runner with a Unity Personal serial from Mentis's account (routine, widely used, one secret). Second fallback is a GitHub macos-26 runner. If ALL fail, the C# importer becomes as untestable as the FBX writer was and Anvil loses much of its advantage — so this trip-wire is non-negotiable and must be reported honestly, not worked around quietly.
- No public evidence exists of a VRM or glTF avatar reaching VRChat without the 0.x converter. VRM Converter for VRChat is pinned to com.vrchat.avatars 3.5.0 and com.vrmc.univrm 0.128.1, last released 2025-01-22, and targets VRM 0.x only. Mitigation: my importer does not use UniVRM or the converter at all — VRM is only the file's shape, and I build the Avatar myself with AvatarBuilder. This is genuinely a case where owning the importer removes the dependency risk rather than adding one. But it is unproven until Mentis's step 7, which is exactly why step 7 is the gate.
- The 'one extra Unity package' is a real regression against the PRD's no-extra-importer promise. Mitigation and honest accounting: it is one double-click, once, in an ecosystem where every creator already installs packages via VCC — and it buys three things an FBX in a ZIP structurally cannot deliver: Mesh Read/Write enabled (off = Very Poor plus a hard upload block), a mobile-whitelist shader, and ASTC texture compression that decides whether a 2048 albedo lands at ~3-6MB (Excellent) or ~21MB (Medium). Position it in onboarding as a benefit, not an apology.
- Byte-determinism across Apple Foundation and swift-corelibs-foundation could break the M2 hash handshake. Mitigation: hand-rolled JSON writer with fixed key order (~150 lines), every float in the binary buffer except POSITION min/max which use fixed formatting, vendored miniz at a pinned level and strategy rather than system zlib whose version differs between platforms, and a CI fixture asserting identical bytes from the Linux and macOS-runner builds before the device is ever involved.
- Skin weight quality cannot be automated to a professional standard, and Blender's heat weighting fails silently — parent_set returns FINISHED with only an RPT_WARNING, and output weights measured 0.976-0.994 per vertex rather than 1.0. Mitigation: transfer the CC0 default_weights.mhw first and use heat only as a per-region fallback; verify by inspecting per-bone weights, never by the operator's return status; prune-to-4, normalise, sort descending, X-mirror; then gate on the pose-metric sweep. One human visual pass remains mandatory and is budgeted as a Mentis touchpoint.
- MSL cannot be compiled on Linux — Apple ships Metal Developer Tools for macOS and Windows only. Mitigation: compile shaders on every push via a macos-26 runner with `xcrun -sdk iphoneos metal -c` (pin the runner image; the Metal toolchain is present on macos-26 but reportedly not installed on Xcode 27, so add an explicit toolchain step). Keep every shader thin and mirror its math in a Swift reference function tested on Linux, then diff GPU against CPU once on device. This is the single largest genuinely-Apple-only surface and no architecture removes it.
- VRChat's mobile ceilings, the pinned Unity version and the SDK's validation rules will move. Unity 6 SDK and VCC were 'going through QA' as of the 2026-08-27 Dev Update and 'In Progress' on the roadmap as of 2026-09-01, while servers still reject anything newer than 2022.3.22f1. Mitigation: put every threshold and the target Unity version in a versioned validation-data file the app reads, never a hard-coded marketing guarantee, and re-run the golden corpus the week the Unity 6 SDK beta ships since Humanoid import behaviour is what could move.
- The template retopology is a bigger job than the PRD implies: the source body is 26,756 triangles, not ~13k, so this is a 3x reduction that must preserve joint edge loops. Decimate is not retopology. Mitigation: budget a real technical-art pass, prototype loop-preserving retopo (QuadriFlow with guide curves) in M1, and gate on Unity pose renders rather than triangle count alone.

**Why better than the PRD.** The PRD's own thesis is right — "the first engineering milestone is not the editor" — but it picks the wrong milestone. It gates the project on the component that is simultaneously the highest-risk, the lowest-value, and the least testable by the person who is actually writing the code.

Consider what the PRD's Phase 0 demands before it can even begin: an Xcode workspace, an iOS static link against an SDK whose last four "iOS" releases ship macOS binaries, a physical iPad, a Mac, and a Unity install. Every one of those is Mentis. The agent's entire contribution to the gate is writing code it cannot run. And what does passing prove? That an FBX exists — after which the file still faces Unity's ModelImporter, whose auto-mapper scores forbidden keywords at -1000, demands UpperArm within 5 degrees of ±X, rejects coincident joints, throws "Ambiguous Transform" on a duplicated node name, and counts hierarchy in weighted-bone steps rather than transforms. None of that is diagnosable from a red cross next to Configure.

Anvil's gate is the same question asked from the other end: can the user get a working avatar? It runs in CI, it produces a diagnosis rather than a boolean when it fails, and Mentis's first involvement is clicking Upload — the last link, not the first.

Six concrete advantages:

1. The highest-risk dependency is deleted rather than mitigated. Three FBX writers, three named verified defects (macOS objects in Autodesk's iOS package; Assimp's position-keyed vertex merge silently violating the PRD's own frozen-order invariant; ufbx-write never emitting a skeleton root). The PRD hedges with a two-candidate gate; Anvil needs none of them, because the format the iPad writes is one the research proved is 54 lines of stdlib code and has a free headless validator.

2. Unity's heuristic mapper is removed from the critical path entirely. Every one of the fifteen-plus Humanoid failure modes catalogued in the research exists only because a tool handed Unity a file and hoped. AvatarBuilder.BuildHumanAvatar with an explicit HumanDescription is what a generator should have been doing all along.

3. Three VRChat requirements become satisfiable that an FBX in a ZIP simply cannot address: Mesh Read/Write (off = Very Poor and blocked upload), the mobile shader whitelist, and ASTC compression deciding which texture-memory bracket a 2048 albedo lands in. The PRD does not track texture memory as a ranked stat at all.

4. The device acceptance test becomes a SHA-256 comparison. The iPad and CI run the same Swift package; identical input must give identical bytes. This is the difference between "Mentis debugs an export on a device" and "Mentis taps a button and the agent reads a hash."

5. VRChat rule violations surface at import with the rule named, from rules read out of the shipping SDK source, instead of as an opaque SDK error after the user has invested in the model.

6. The desktop was never optional. The PRD already says "move the ZIP to a Mac or PC." Unity 2022.3.22f1 is mandatory for upload and is desktop-only. Anvil does not add a machine to the workflow — it puts a machine that was already required to work, doing the one job it is uniquely good at.

The trade is honest and should be stated plainly: one Unity package install replaces the "drag one FBX in" promise. That is the whole cost. Every VRChat creator already installs packages, and there is currently no iPad app in existence that reaches a rigged VRChat avatar at all — the closest incumbent, VRoid on iPad, exports VRM and needs a full desktop optimization toolchain (Meshia, Avatar Optimizer, TexTransTool, Modular Avatar, lilToon, NDMF) to escape Very Poor. Anvil's differentiator is not "sculpt on iPad," which is well served. It is deterministic protected topology that lands at Mobile Good by construction with a one-package desktop step.

**Weakest point.** Anvil trades one untestable component for another, and I should be blunt about it rather than let the CI story obscure it.

The PRD's untestable risk is an iOS FBX writer. Mine is a Unity C# ScriptedImporter. I claim mine is testable because Unity 2022.3.22f1 ships a Linux Editor with documented -batchmode -nographics -executeMethod. But the research flagged this UNKNOWN twice and never resolved it: whether Unity licenses non-interactively in a container, and whether the VRChat SDK's own validation can be driven in batchmode without an interactive login. No VRChat page describes headless SDK use at all. If Unity-on-Linux cannot be licensed, the importer becomes exactly as Mac-dependent as the FBX writer was, and I will have moved the problem rather than solved it — while having also spent a milestone building an importer. That is why proving it is day 1 of Phase 0 and not day 5, and why I would report a failure there as a genuine architecture blow rather than routing around it quietly.

The second weakness is narrower but sharper: nobody has publicly shipped a VRM or glTF avatar into VRChat without the 0.x converter. The whole chain up to the prefab is provable in CI, and the last centimetre — does the VRChat SDK accept an avatar whose Avatar was built by AvatarBuilder rather than imported from an FBX — has no published precedent either way. My importer sidesteps the converter's staleness, but it does so into unmapped territory. I believe it works, because the SDK validates the Unity Humanoid Avatar and not the source file format, and because impostor generation likewise depends only on the Humanoid mapping. But "I believe it works" is precisely the standard the PRD was right to reject, and only Mentis's thirty minutes settles it.

Third, smaller, worth naming: my headlessTestablePercent of 68 is generous about the paint and render layers. I can test the CPU reference implementations of UV stamping, seam handling and dilation on Linux, and I can mirror every shader in Swift and diff them — but a mirrored implementation proves the math, not the pixels. Whether a full-texture 2048² dab pass holds the frame budget on an A14, and whether a stroke feels like ink or like lag, are questions no amount of CI answers. If the Pencil feel is wrong, everything above it is irrelevant, and that is the one part of this plan where the agent can only build, never judge.
