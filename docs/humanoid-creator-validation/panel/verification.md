# Adversarial verification of load-bearing research claims (Opus refuters, 2026-09-03)

Refuters were told to default to `refuted=true` unless they could re-verify from primary sources; read each correction — most confirm the conclusion and fix a detail.


## [REFUTED / high] VRChat's SDK requires MORE humanoid bones than Unity's Mecanim minimum. Beyond Unity's 15 required bones (Hips, Spine, Head, and L/R UpperArm, LowerArm, Hand, UpperLeg, LowerLeg, Foot), the VRChat build panel errors unless Chest, Neck and both Shoulders are also mapped ('Pelvis, Spine, Chest, Neck and Shoulders ... must all be mapped'), and the Shoulders and Neck must be direct children of the Chest bone. Head, hands and feet must be mapped. Optional for SDK3: UpperChest (fine to map — the old IK warning is SDK2-only), fingers (SDK3 'has no problem with using armatures without finger bones'; FBT/finger warning is SDK2-only), toes, eye bones (only needed for Eye Look), jaw bone (only needed for Jaw Flap lip sync).

Mostly right, but one clause is wrong in a way that will break the exporter, and it is wrong because the cited doc page is stale. I decompiled nothing — I pulled the current shipping SDK source from VRChat's own VPM listing (packages.vrchat.com/official?download → com.vrchat.avatars 3.10.4, latest stable; 3.10.5-beta.2 is the newest listed) and read the validator: av310/Editor/VRCSDK/SDK3A/VRCSdkControlPanelAvatarBuilder.cs, method AnalyzeIK() at line 4093.

WHAT HOLDS (verified in current SDK source, not just docs):
- Extra-bones-beyond-Mecanim is correct and still enforced. Line 4143: `if (null == neck || null == lClav || null == rClav || null == pelvis || null == torso || null == chest)` → `_builder.OnGUIError(ad, "Spine hierarchy missing elements, please map: " + missingElements)` → `return false`. So Chest, Neck, LeftShoulder and RightShoulder are hard requirements on top of Unity's 15. Total = 19 bones.
- These are genuinely build-BLOCKING, not cosmetic. OnGUIError feeds the GUIErrors dictionary (base310/.../ControlPanel/VRCSdkControlPanelBuilder.cs), and CheckAvatarForValidationIssues() (avatar builder line 3888) throws `new ValidationException("Avatar validation failed", errorsList)` when `!NoGuiErrorsOrIssuesForItem(...)`. The V3 UI gates the build button on the same predicate.
- "Humanoid avatar must have head, hands and feet bones mapped." is verbatim in the source (line ~4119) and is an OnGUIError with an early `return false`.
- Fingers optional in SDK3: CONFIRMED at the source level, stronger than the doc claims. The three-finger check is wrapped in `#if VRC_SDK_VRCSDK2` (both the `bool hasThreeFingers` declaration and the check body), so it does not compile at all in an SDK3-only project.
- UpperChest IK warning is gone: CONFIRMED. There is no "UPPERCHEST ... will cause problems with IK" string anywhere in 3.10.4. The only UpperChest references are the hierarchy branch below.
- Toes, eyes, jaw: no build validation touches HumanBodyBones.LeftToes / LeftEye / RightEye / Jaw at all in AnalyzeIK. They are avatar-descriptor features (Eye Look, Jaw Flap viseme mode) as stated.
- Unity's "A minimum of 15 bones" is verbatim on docs.unity3d.com/Manual/UsingHumanoidChars.html, and that page does NOT enumerate which 15 — the claim's own evidence correctly flags the list as inferred from HumanTrait.RequiredBone / the 2014 blog. The inferred 15 is right.

THE MATERIAL ERROR — the hierarchy rule:
The claim says "the Shoulders and Neck must be direct children of the Chest bone" while ALSO saying UpperChest is fine to map. Those two together produce a rig that fails validation. The current SDK is conditional (lines 4157-4166):

    if (null != upperChest)
        correctSpineHierarchy = lClav.parent == upperChest && rClav.parent == upperChest && neck.parent == upperChest;
    else
        correctSpineHierarchy = lClav.parent == chest && rClav.parent == chest && neck.parent == chest;

and the error text was updated to match: "Spine hierarchy incorrect. Make sure that the parent of both Shoulders and the Neck is the Chest (or UpperChest if set)." — also an OnGUIError with `return false`.

Corrected statement: the parent of both Shoulders and the Neck must be the HIGHEST MAPPED chest bone — UpperChest if UpperChest is mapped, Chest otherwise. Mapping UpperChest is allowed in SDK3, but doing so MOVES the required attachment point; shoulders/neck parented to Chest with UpperChest also mapped is a build-blocking error. For an exporter the safest output is: do not map UpperChest at all, and parent LeftShoulder, RightShoulder and Neck directly to Chest. Either way the two decisions are coupled and cannot be made independently.

WHY THE CLAIM GOT IT WRONG: creators.vrchat.com/avatars/rig-requirements/ still says "make sure that the parent of both Shoulders and the Neck is the Chest" with no UpperChest caveat — the page's own "significantly out of date" banner is doing real work here. The claim inherited a stale doc string that the SDK itself no longer prints. The ask.vrchat.com moderator reply (13 Jan 2026) is a community moderator, not staff, so it corroborates the Chest requirement but is not primary; the SDK source is.

TWO ADDITIONS THE CLAIM OMITS, both build-blocking OnGUIError paths in the same file and both relevant to a generative iPad exporter:
- Scale gate: "This avatar is too short. The minimum is 20cm shoulder height." is an ERROR (shoulderPosition.y < 0.2f). Over 5m shoulder height is only a warning. So the exported rig must be at least 20cm tall at the shoulder in Unity units.
- Limb ordering: LowerArm must be the FIRST child of UpperArm, Hand the first child of LowerArm, and likewise LowerLeg/Foot (`lShoulder.GetChild(0) == lElbow` etc.). These are OnGUIWarning, not errors, so they will not block upload — but a generated skeleton that emits twist bones or attachment points ahead of the next limb bone in child order will silently break forearm/shin rotation in-game. Also warning-only: split hierarchy (Hips not an ancestor of all humanoid bones).

## [REFUTED / high] The official Creator Companion GUI is Windows-only: 'The Creator Companion is only fully-supported on Windows 10'; Mac and Linux get the VPM command-line tool only, which 'should be able to make new projects from templates, add packages to projects and most other functions' but could not locate Unity Hub/Editor until 2.5.0-beta.2 (25 June 2026): 'VPM Command Line Interface tool no longer requires unity or unity hub configured on the system. The community-maintained ALCOM (built on vrc-get) is a cross-platform (Windows/macOS/Linux) VCC replacement that shares VCC's settings and is discussed on ask.vrchat.com. This matters because Mentis is on a Mac: the PRD's user step 'Install VRChat Creator Companion and its selected Unity version' is not literally possible on macOS via the official GUI.

The claim's core conclusion is correct and verified, but two elements are materially wrong and must be corrected.

VERIFIED (verbatim from primary sources): vcc.docs.vrchat.com/guides/getting-started/ states "The Creator Companion is only fully-supported on Windows 10 (Windows 11 may work but is not fully tested)" and directs non-Windows users to "Linux/macOS for a command-line interface". vcc.docs.vrchat.com/vpm/cli/ states "The only fully-supported platform at the moment is Windows 10", tells Mac users "You should be able to make new projects from templates, add packages to projects and most other functions", and says of Linux "The system is completely untested on Linux distributions at this point, but may work anyway due to the work done for the Mac version." The docs landing page offers a Windows-only download, states "The Creator Companion supports Windows 10 and 11 (64-bit)" and "Other operating systems are not fully supported." ALCOM is genuinely cross-platform ("a cross-platform application available on Windows, macOS, and Linux"), unofficial/community-maintained, announced on ask.vrchat.com (anatawa12, 1 Jan 2025), and states "It uses the same settings file as VCC wherever possible." The claim is also right to reject the search snippet about a macOS VCC download: AranoYuki1/VCC-for-mac is explicitly an "Unofficial macOS Client". The bottom line stands: there is no official macOS GUI build, so the PRD step "Install VRChat Creator Companion and its selected Unity version" is not literally possible on macOS via the official GUI.

ERROR 1 - "could not locate Unity Hub/Editor until 2.5.0-beta.2" is FALSE for macOS. That limitation is documented ONLY in the Linux Setup section: "The VPM will not be able to find your Unity Hub or Unity Editor paths however, so you'll need to update your settings.json file to set them manually for now." The Mac Setup section documents a working detection path that predates 2.5.0: install Unity Hub for Mac and Unity 2022.3.22f1, then "Run vpm check hub to find and save the location of Unity Hub" (default /Applications/Unity Hub.app/Contents/MacOS/Unity Hub) and "Run vpm check unity to find and save the location of the Unity Editor." The claim generalizes a Linux-only limitation to the Mac case. It also misreads the release note: the CLI "no longer REQUIRES unity or unity hub CONFIGURED on the system" describes removal of a hard prerequisite (the CLI previously refused to operate without them), not the addition of Unity detection.

ERROR 2 - The 2.5.0 change is PRERELEASE-ONLY and has not shipped stable. The VCC docs news index lists Release 2.5.0-beta.2 (25 June 2026) as the newest entry; the latest STABLE release is 2.4.5 (10 December 2025). As of 2 September 2026 there is no stable 2.5.0. The claim presents the non-Windows unblock as an accomplished, dated fact without noting it is available only in a beta. Additionally, the quoted CLI line sits in 2.5.0's main "Changes" section (spanning beta.1 to beta.2), not in the "Changes between 2.5.0-beta.1 and 2.5.0-beta.2" delta, so attributing it specifically to beta.2 is imprecise.

ADDITIONAL CAVEAT on the ALCOM settings-sharing point: VCC 2.5.0 introduces a new settings_v2.json file "required to create a new settings format with clear versioning strategy and to avoid situations where older tools would fully overwrite the settings file" - i.e. it deliberately fences off the shared-settings.json arrangement ALCOM depends on. ALCOM's latest release (1.1.8) contains no release-note mention of settings_v2.json support. So "shares VCC's settings" is accurate against today's stable VCC (2.4.5) but is not guaranteed once 2.5.0 ships.

CORRECTED STATEMENT: The official Creator Companion GUI is Windows-only ("only fully-supported on Windows 10"), with a Windows-only download and no official macOS or Linux build; non-Windows users are directed to the VPM CLI, which on macOS has had a documented working setup path (vpm check hub / vpm check unity) since well before 2.5.0 and "should be able to make new projects from templates, add packages to projects and most other functions", while Linux is "completely untested" and is the platform where VPM "will not be able to find your Unity Hub or Unity Editor paths". A change removing the Unity/Unity-Hub configuration requirement entirely ("This unblocks the usage of VPM CLI on non-Windows platforms") exists only in the 2.5.0 BETA line (2.5.0-beta.2, 25 June 2026); the newest stable remains 2.4.5 (10 Dec 2025). The unofficial, community-maintained ALCOM (built on vrc-get) is a genuine cross-platform Windows/macOS/Linux VCC alternative that currently shares VCC's settings file, though VCC 2.5.0's new settings_v2.json is explicitly designed to stop older tools overwriting shared settings. The practical conclusion is unchanged: on macOS, Mentis cannot follow the PRD step via the official GUI, and the PRD should instead specify Unity Hub + Unity 2022.3.22f1 (Apple Silicon builds exist) plus either the VPM CLI or ALCOM to add the VRChat SDK packages.

## [REFUTED / high] Skin-weight QUALITY cannot be automated to professional standard, but acceptable weights for a stylised mannequin can be produced once, offline and headlessly, with Blender's bone-heat method (Baran & Popović 2007) and then frozen into the template. The math: solve per bone i the sparse linear system (-Δ + H) w_i = H p_i, where Δ is the cotangent surface Laplacian, p_i[j] = 1 if bone i is the nearest bone visible from vertex j (1/k for k equidistant bones), H = diag(c / d(j)²) with d(j) = distance from vertex j to its nearest bone and H_jj = 0 when the vertex-to-bone segment leaves the volume; c = 1. ## [REFUTED / high] Unity accepts Blender-exported FBX by construction: Unity's own `.blend` import path launches Blender and runs Blender's Python FBX exporter (`Unity-BlenderToFBX.py`, shipped in the Editor's Tools folder, e.g. 6000.0.25f1). Unity's legacy manual states "Unity natively imports Blender files. This works under the hood by using the Blender FBX exporter"; the current Unity 6.6 manual says proprietary files are converted by launching the modelling software in the background and recommends "export to the .fbx format wherever possible". Blender's exporter even ships a `defaults_unity3d()` preset (axis_up 'Y', axis_forward '-Z', object_types {'ARMATURE','EMPTY','MESH','OTHER'}, use_armature_deform_only True). Therefore a Blender-generated FBX is a sound *golden reference* file for the PRD corpus. HOWEVER, 'imports' is not 'auto-maps as Humanoid': that depends on bone hierarchy/naming/rest pose and must still be confirmed in the VCC-selected Unity on Mentis's Mac (community VRChat guidance: uncheck Add Leaf Bones, FBX All scaling, bone axes Y/X, ~90° rest X). A Jan-2026 community note also reports Unity 6.3 LTS needing 'Bake Axis Conversion' for .blend imports, so axis behaviour should be re-verified on the exact Unity version.

The mechanism half is confirmed verbatim, but the `defaults_unity3d()` limb — the part doing the load-bearing work for "by construction" and for the humanoid settings — is materially wrong, and it is wrong in the direction that matters for a rigged-avatar PRD.

CONFIRMED (read directly):
- Unity 5.3 manual, verbatim: "Unity natively imports Blender files. This works under the hood by using the Blender FBX exporter." (plus "You need to have Blender version 2.60 or later").
- Unity 6.6 (6000.6) HOWTO-ImportObjectsFrom3DApps, verbatim: "When Unity imports a proprietary file, it launches the 3D modeling software in the background" and "You should not use these file formats in production; instead, export to the .fbx format wherever possible."
- `Unity-BlenderToFBX.py` does ship at `Editor/Data/Tools/` in Unity 6 (present in 6000.0.25f1 per the gist and in a full dump of stock 6000.0.48f1).
- `defaults_unity3d()` does exist in `blender/blender` `scripts/addons_core/io_scene_fbx/export_fbx_bin.py` (line 3649) with exactly the values quoted: axis_up 'Y', axis_forward '-Z', global_matrix Rotation(-pi/2,4,'X'), bake_space_transform False, object_types {'ARMATURE','EMPTY','MESH','OTHER'}, use_armature_deform_only True, add_leaf_bones False, primary/secondary_bone_axis 'Y'/'X', mesh_smooth_type 'FACE'.

CORRECTIONS:
1. `defaults_unity3d()` is NOT a shipped, exercised preset. It has ZERO callers anywhere in the Blender tree (grep of the file: the only occurrence is the definition; GitHub code search over blender/blender: total_count 1, the definition). It is not exposed in Blender's FBX export UI presets. It is vestigial reference code, not something Blender or Unity runs.
2. Unity does not use it on any live path. Stock `Unity-BlenderToFBX.py` (verified against a complete dump of Unity 6000.0.48f1) calls `io_scene_fbx.export_fbx.defaults_unity3d()` ONLY inside the `blender 2.59-2.79` else-branch — and `io_scene_fbx.export_fbx` is the ASCII FBX 6.1 exporter Blender REMOVED in 2.80 (developer.blender.org T53877). That branch is unreachable for every modern Blender. For Blender 2.80+ the script takes the `blender280` branch and calls:
   bpy.ops.export_scene.fbx(filepath=outfile, check_existing=False, use_selection=False, use_active_collection=False, object_types={'ARMATURE','CAMERA','LIGHT','MESH','OTHER','EMPTY'}, use_mesh_modifiers=True, mesh_smooth_type='OFF', use_custom_props=True, bake_anim_use_nla_strips=False, bake_anim_use_all_actions=False, apply_scale_options='FBX_SCALE_ALL')
   Note what is ABSENT: add_leaf_bones, use_armature_deform_only, axis_up/axis_forward, global_matrix, bake_space_transform, primary/secondary_bone_axis. Those fall back to Blender's operator defaults, which I verified in io_scene_fbx/__init__.py are `add_leaf_bones` default=True (line 467-472) and `use_armature_deform_only` default=False (line 495-499). So Unity's own .blend path exports WITH leaf bones and WITH non-deform bones — precisely the two things the VRChat/humanoid community guidance quoted in the claim tells you to turn off. Unity's .blend path is therefore evidence AGAINST using it as a rigged-humanoid reference, not evidence that Unity blesses those settings. (It also explains the well-known Unity .blend bug that only the first action imports: bake_anim_use_all_actions=False.)
3. The gist's export arguments are the gist AUTHOR'S hand-edited replacement, not Unity's shipped code — he states he deliberately did not redistribute Unity's file. So `use_space_transform=False, axis_forward='-Y'/'Y', axis_up='Z'` are one person's workaround, paired with his 2026-01-16 note to tick "Bake Axis Conversion" on Unity 6.3 LTS. Treat that as a single uncorroborated community datapoint about a modified script, not as documented Unity 6.3 behaviour.
4. creators.vrchat.com/avatars/rig-requirements/ does not support the parenthetical settings list: it says nothing about Add Leaf Bones, FBX import scale, or bone axes (its only bone-axis mention is eye bones), and it opens with "This page is significantly out of date, but should still be mostly accurate." It does require head/hands/feet mapped and Pelvis/Spine/Chest/Neck/Shoulders mapped.

CORRECTED CLAIM: Unity does convert .blend by launching Blender and invoking `bpy.ops.export_scene.fbx`, which confirms only that Unity ingests Blender-produced FBX in general. It confirms nothing about the export flags a humanoid golden reference needs, because Unity's live branch passes none of them and inherits Blender defaults (leaf bones ON, deform-only OFF) that are wrong for a VRChat humanoid. `defaults_unity3d()` is uncalled dead code in Blender and is reached by Unity only through a branch requiring a module deleted in Blender 2.80. For the PRD, a Blender-exported FBX is still a reasonable golden reference, but ONLY if the flags are set EXPLICITLY (add_leaf_bones=False, use_armature_deform_only=True, primary/secondary_bone_axis 'Y'/'X', apply_scale_options='FBX_SCALE_ALL', axis_up 'Y' / axis_forward '-Z') — never inherited from Unity's .blend path or assumed from `defaults_unity3d()`.
