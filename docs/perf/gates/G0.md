## 1. The blocker

`index.html` (worktree line ~9589), inside `__BIRB.effective()`:

```js
statsPath: (bloomPass && bloomEnabled && adaptiveTier.getTier() < 1)
  ? 'bloom-frameStats' : 'renderer-info',
```

This is not a live read. It re-evaluates `presentFrame()`'s own branch predicate and reports
the answer as if it were an observation. Four reasons it has to be fixed before Wave 1 rather
than after:

1. **It violates the criterion verbatim.** ULTRACODE §4 Wave 0: *"no field of `effective()` is
   derived from `tier` or `DPR_CAP` — a hook that reports what the code meant to do cannot
   catch the desync this whole programme is about."* This field is derived from `tier`.
2. **It contradicts the contract it ships beside.** CONTRACT.md §0 defines **effective** as
   *"read back off the live object that renders … Never recomputed from intent."* §0 and TEL-19
   cannot both be right, and cheap-tier agents are instructed to transcribe from that document.
3. **The correct observable already exists, in this same diff, and was measured.**
   `frameTotals().passes` is 5 at tier 0 and 1 at tiers 1 and 2 (evidence below) — the branch
   that actually ran, counted by the frame that ran it. `statsPath` can be derived from that,
   or from a boolean latched inside `presentFrame()`.
4. **The cost only rises.** TEL-19 is already a contract row and a register row, so Wave 1
   authors assertions over it and Wave 2 surfaces it in the panel. Fixing it now is one field;
   fixing it at G2 is a field, an assertion, a panel row and two documents.

**Required before re-gate**

- Derive `statsPath` from observed behaviour (latch the branch in `presentFrame()`, or read
  `frameRenderTotals.passes`), or delete the field.
- Update CONTRACT.md TEL-19 (line 231) and `requirements.json` TEL-19 to name the observed
  source. Per the amendment rule this is a gate decision, and this file is it.
- No other change. Do not touch the five P0.2a fields — they are correct and are the reason
  the rest of this gate passes.

## 5. Amendment — blocker remediated, re-gated (orchestrator, Opus 5)

The STOP above was correct and is left standing as the record. It is now closed.

### What was wrong

`presentFrame()` (index.html) branches on `bloomPass && bloomEnabled && adaptiveTier.getTier() < 1`.
`effective().statsPath` re-evaluated that same predicate and reported the answer as an observation.
That is the failure mode ULTRACODE §4 names as a Wave 0 STOP: a probe that recomputes intent cannot
see the case where intent and reality have come apart, which is the only case the workbench exists for.

### The fix

`frameRenderTotals` gained a `statsPath` field. `presentFrame()` **latches it inside the branch it
actually takes** — `'bloom-frameStats'` immediately before delegating to the bloom pass, `'renderer-info'`
immediately before the direct render. `effective()` now returns that latch and computes nothing.

The field is therefore a record of control flow that executed, not a prediction of control flow that
should execute. It is corroborated by `frameTotals().passes`, which is accumulated by `tallyRenderPass()`
through a completely different mechanism — so the two disagree if either is wrong.

### Re-verification (run after the fix, at the contract's pinned mobile context)

```
node tools/birb-shot.mjs --start --eval 'window.__BIRB.pinTier(N)' \
  --after '(()=>{const e=__BIRB.effective(),f=__BIRB.frameTotals();
           return {tier:N,statsPath:e.statsPath,passes:f.passes,dpr:e.rendererPixelRatio};})()'

tier 0 -> exit 0  {"tier":0,"statsPath":"bloom-frameStats","passes":5,"dpr":1.7}
tier 1 -> exit 0  {"tier":1,"statsPath":"renderer-info",   "passes":1,"dpr":1}
tier 2 -> exit 0  {"tier":2,"statsPath":"renderer-info",   "passes":1,"dpr":0.85}
```

`statsPath` and `passes` agree at every tier by two independent routes, and the DPR discriminator
(1.7 / 1.0 / 0.85) remains alive.
